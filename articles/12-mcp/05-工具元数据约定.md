# MCP工具的元数据约定 名字描述schema

MCP 协议要求每个工具暴露元数据。chayuan-desktop 桌面单机版基于这些元数据让 LLM 知道怎么调用工具。这一篇讲元数据约定。

MCP 工具的核心元数据。

字段一：name。工具的唯一标识。比如 search_kb、execute_sql、send_email。命名要表达功能。

字段二：description。工具的人类可读描述。比如 在指定知识库中按自然语言检索相关内容。LLM 看这个决定是否调用。

字段三：inputSchema。工具的参数 schema（JSON Schema 格式）。LLM 按 schema 知道每个参数的类型和必需性。

inputSchema 示例。

```
{
  "type": "object",
  "properties": {
    "query": {"type": "string", "description": "查询内容"},
    "ku_ids": {
      "type": "array",
      "items": {"type": "string"},
      "description": "知识库 ID 列表"
    }
  },
  "required": ["query"]
}
```

LLM 看到这个 schema 就知道 query 是必填字符串，ku_ids 是可选数组。

LLM 调用时的约定。

LLM 收到 system prompt 含工具元数据列表。

LLM 决定调用工具时输出 tool_call 块（含 name 和 arguments）。

chayuan-desktop 校验 arguments 符合 inputSchema。

调用工具，等结果。

把结果返回给 LLM。

LLM 基于结果生成最终答案。

description 写得多详细才有效。

描述要包含。

功能定位。这个工具做什么。

何时使用。什么场景下该调。

参数说明。每个参数的含义。

返回说明。结果格式。

边界情况。什么时候不能用。

description 太短，LLM 不会调；太长，浪费上下文。一般 100-300 字符合适。

中文 description。chayuan-desktop 内置工具的 description 都是中文。LLM 看中文 prompt 能正确调用。混合中英文也行。

inputSchema 的细致。某些参数有 enum 限制（type: status 只能是 active 或 inactive）。schema 里写 enum 列表，LLM 不会乱传。

错误处理的元数据。chayuan-desktop 的 MCP 工具在 inputSchema 里标注哪些错误情况，LLM 能预期并处理。比如 KB 不存在 是预期错误，LLM 应该告诉用户。

版本管理。某些工具有版本（v1、v2）。chayuan-desktop 在工具名里带版本（search_kb_v2），让 LLM 调用时不混淆。

WPS AI 插件 chayuan-wps 共用同一份 MCP 工具元数据。

MCP 工具的元数据约定是工具被 LLM 正确调用的基础。免费开源的AI软件 想让 LLM 用工具用得顺，元数据精细写是关键。chayuan-desktop 在这一面的写作规范让工具调用准确率提升。
