# MCP 工具的并发 同时多个调用的资源管理

chayuan-desktop 桌面单机版的 MCP 工具在并发调用时有资源管理。这一篇讲。

## 并发的场景

场景一：LLM 一轮决定调多个工具。比如 同时查 GitHub 和 Slack。

场景二：用户同时跑多个对话窗口。每个都在调工具。

场景三：后台任务和前台对话都用工具。

## 并发的瓶颈

每个 MCP 工具是独立子进程。stdio 通信是单连接（不并发）。

如果同时两个调用到同一工具。工具自己是否能并发处理。看实现。

某些工具是单线程顺序处理（像 Python 单线程跑 asyncio）。能跑多个调用但本质是排队。

某些工具能多线程或多进程处理。真正并发。

chayuan-desktop 不假设工具一定支持并发。默认按 单工具实例顺序处理 调度。

## 多实例工具

某些工具频繁被调，单实例不够快。chayuan-desktop 配置里能开多实例。

```yaml
mcp_servers:
  github_mcp:
    instances: 3
```

chayuan-desktop 启动 3 个子进程。请求轮询分发到 3 个。

代价。多占内存。每实例可能 50-200MB。

## 工具调用的优先级

某些场景区分优先级。

交互式（用户在等）：高。

后台（异步任务）：低。

chayuan-desktop 的请求队列按优先级调度。高优先级请求插队。

## 资源隔离

工具子进程的资源限制（前面文章讲）。每工具最多 50% CPU、2GB 内存。

并发多个调用时合在一起最多就这些资源。

## 工具调用的超时

每次工具调用有超时（默认 30 秒）。避免某调用卡住占用 slot。

超时后 chayuan-desktop 杀掉进程。如果是单实例工具，重启子进程。如果是多实例，只重启卡住那个。

## 跨工具的并发

不同工具同时调用没冲突。chayuan-desktop 一轮 LLM 决定调用 github + slack 时同时启动两个工具调用。等都完成后给 LLM 看结果。

某些 LLM 框架支持工具并行调用（Anthropic、OpenAI 都支持 parallel_tool_calls）。chayuan-desktop 跟随。

## 死锁避免

某工具 A 调用过程中又调工具 B。如果 B 又依赖 A 的回复。死锁。

实际场景少见。chayuan-desktop 的检测。一个工具调用过程中如果尝试调同一工具的子进程实例，直接拒绝。

## 队列长度限制

并发请求过多。每个工具最多排队 100。超过返回 工具繁忙 错误给 LLM。

避免 OOM 或长时间等待。

## 国产化场景

党政军场景日常用户量不大，并发有限。chayuan-desktop 默认配置够用。

某些场景需要批量处理（比如 1000 文档自动 OA 标记）。配置多实例 + 资源放宽。

## chayuan-server 的对应

chayuan-server 多用户场景下并发管理更复杂。chayuan-desktop 单机简化。

## WPS 加载项

chayuan-wps 在 WPS 里发起的工具调用跟桌面端共享资源池。统一调度。

## 总结

MCP 工具的并发是 chayuan-desktop 在工具调用规模化上的工程能力。免费开源的AI软件 让 多工具并行 不冲突不饥饿。chayuan-desktop 的队列 + 多实例 + 优先级 + 超时让 工具调用 在工程上稳。
