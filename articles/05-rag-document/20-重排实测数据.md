# 重排模型对最终答案的影响 一组实测数据

chayuan-desktop 桌面单机版默认开启重排（rerank）。重排到底对答案质量有多大影响是用户经常问的问题。这一篇用一组实测数据讲清楚重排的收益。

先看重排是什么。文档 RAG 第一阶段是 向量召回（retrieve）：给 query 算嵌入，去 sqlite-vec 找距离最近的 K 个 chunk。第二阶段是 重排（rerank）：把召回的 K 个 chunk 跟 query 一起送给重排模型，让它打更精确的分数，重新排序。最终拿前 N 个（N < K）喂给 LLM。

重排的价值。向量召回是 单塔 模型的双向距离计算，每个 chunk 的向量是预先算好的。query 跟 chunk 之间的细粒度交互不被建模。重排是 双塔 或 cross-encoder，每次实时把 query 跟 chunk 一起跑模型，能捕捉更细的语义关联。代价是慢（每个 chunk 跑一次模型）。

实测对比。chayuan-desktop 在自家 KB recall 评估集上跑过两组对比。

第一组：纯向量召回，top-K=10。recall@5 = 0.78（前 5 个里包含 ground truth 命中的概率）。recall@10 = 0.85。

第二组：向量召回 + 重排，召回 top-20，重排选 top-5。recall@5 = 0.91。提升约 13 个百分点。

第三组：向量召回 + 重排，召回 top-50，重排选 top-5。recall@5 = 0.93。比 top-20 又提升 2 个百分点。但是延迟从 200ms 变到 400ms。

结论一。重排带来的精度提升是显著的，约 10-15 个百分点。

结论二。召回 K 越大重排基础越宽，精度越高，但延迟也涨。chayuan-desktop 默认召回 top-30，重排选 top-5，是 精度 / 延迟 的好平衡。

结论三。不同 KB 的重排收益不同。专业领域 KB（法律、医学）的重排收益更高（细粒度词义匹配很重要）。通用 KB 的收益小一些。

延迟的代价。chayuan-desktop 用的 bce-reranker-base 在 CPU 上每个 chunk 跑约 30-50ms。重排 30 个 chunk 大约 1 秒。GPU 上快 5-10 倍。这个延迟对用户体感可接受（LLM 调用本身就要几秒）。

重排能不能关。chayuan-desktop 让用户在 KB 设置里关重排（为了速度）。关掉之后召回完直接给 LLM，节省 1 秒延迟。

重排模型的选择。bce-reranker 是网易开源的中文重排模型。chayuan-desktop 默认用。其他选择：bge-reranker（智源）、Cohere reranker（云端 API）。每个有自己的精度延迟特征。

重排能力的边界。重排模型对训练数据中常见的语义模式擅长，对极小众领域可能不准。比如医学专业术语在通用重排模型上表现一般。这种场景考虑领域专门重排模型。

重排的隐性收益。一是去重。两份相似 chunk 在召回里都出现，重排能识别并降权。二是去噪。某些 chunk 仅 关键词匹配 但语义不相关，重排能识别。三是 query 意图理解。同一个关键词在不同 query 下的相关 chunk 不同，重排能 query-aware 地区分。

什么场景下重排收益更显著。

场景一：复杂 query。多个限定条件、长 query，向量召回精度下降，重排起补救作用。

场景二：精确事实问答。需要精确命中那一段事实。重排能帮提升 top-1 的精度。

场景三：多源混合检索。重排在跨源结果归一化时有用。

什么场景下重排不那么必要。

场景一：高度相关的小 KB。所有 chunk 跟 query 相关度都不错，重排区分度低。

场景二：极致延迟敏感。需要 1 秒内出答案，重排的几百毫秒不能省。

国产化支持下的重排。bce-reranker 是国产模型，国产化场景天然优选。麒麟 UOS 上 ONNX Runtime 跑 bce-reranker 性能跟主流 Linux 一致。

WPS AI 插件 chayuan-wps 共用同一份重排模型。在 WPS 里检索时重排开关跟桌面客户端一致。

重排实测数据是 chayuan-desktop 给 默认开重排 这个决定的实证支持。免费开源的AI软件 不应该靠 直觉 设默认值，用实测数据决定才是工程化态度。chayuan-desktop 的默认配置是这种态度的体现。
