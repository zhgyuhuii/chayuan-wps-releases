# 本地离线知识库的大文件解析 内存控制与流式策略

chayuan-desktop 桌面单机版偶尔遇到很大的文档：几百页 PDF、几十万行 CSV、几百兆 Excel。这些大文件如果一次性加载到内存会让 sidecar OOM。这一篇讲 chayuan-desktop 的内存控制策略。

先看常见的大文件场景。

场景一：大型标书。500-1000 页 PDF，含大量扫描页和表格。

场景二：历史归档。一份打包的 100 篇文档合订 PDF。

场景三：大型 Excel。十几万行数据 + 多个 sheet + 公式计算缓存。

场景四：长 markdown。一份完整的项目 wiki 导出 markdown，几万行。

如果没内存控制会怎样。一份 500MB 的 PDF 加载到内存可能膨胀到 2-3GB（PyMuPDF 解析 + chunk 列表 + 嵌入向量），单机版 sidecar 在 8G 内存机器上直接 OOM。

chayuan-desktop 的策略一：流式解析。PyMuPDF、openpyxl 都支持按页/按 sheet 流式读取，不一次性加载整个文件。chayuan-desktop 的 parser 用流式 API，每读一页/一 sheet 处理完就释放内存。

策略二：分批入库。chunk 列表不一次性写盘，按批（默认每 100 chunk）写入 sqlite-vec。写完一批就清内存里的 chunk 缓存。这样内存里同时只持有当前批。

策略三：嵌入计算分批。bge-m3 嵌入计算的 batch size 默认 32。一次给模型 32 个 chunk 算嵌入，算完释放。即使整个文档有几万 chunk，内存峰值也只是当前批 + 模型权重。

策略四：超大文件警告。如果文件超过 200MB，chayuan-desktop 在导入时给用户警告 大文件解析可能耗时数十分钟，确认继续。让用户做心理准备。

策略五：内存监控。chayuan-desktop 的 sidecar 在解析过程监控自身内存使用，超过阈值（默认 80% 系统内存）时自动减小批大小或暂停。极端情况下放弃当前文件并报错，避免 OOM 崩溃。

策略六：磁盘缓存。某些中间数据（OCR 结果、嵌入向量）chayuan-desktop 写到 CHAYUAN_ROOT/cache 临时文件，不全部驻留内存。处理完该文件后清缓存。

实测内存占用。chayuan-desktop sidecar 处理一份 500MB 的 PDF 时内存峰值约 1.5G（含模型权重）。如果不开 OCR 兜底，内存峰值约 800MB。8G 内存机器扛得住。16G 机器轻松。

并发处理大文件。chayuan-desktop 默认串行处理大文件（一次只解析一个），避免多个大文件同时占内存。如果你需要并发（比如 folder-sync 一次扫到几个大文件），系统按 CPU 核数限制并发，但每个核的内存预算单独算。

用户可以做的优化。

把大 PDF 拆成小 PDF。500 页 PDF 拆成 5 份 100 页的，分别入库。chayuan-desktop 不强求，但用户场景能拆就拆。

把大 Excel 拆成单 sheet。每个 sheet 单独 import，chayuan-desktop 处理小文件更快。

把大 markdown 按章节拆。markdown 的 heading 天然是分章的位置，用脚本拆分。

OOM 后的恢复。如果 sidecar 真 OOM 退出，Tauri 主进程会自动重启 sidecar。已经入库到 SQLite 的 chunk 不丢（事务保证），未入库的丢。用户重新导入即可。

流式解析的局限。流式解析适合 顺序读 的格式（PDF 按页、Excel 按行）。对 随机访问 格式（比如某些 ZIP 内嵌结构）支持有限。chayuan-desktop 当前对主流办公格式都支持流式。

国产化支持下的大文件。政企客户的标书和归档常常超大。chayuan-desktop 在国产化场景下的内存优化是必经工程。

WPS AI 插件 chayuan-wps 不直接处理大文件，所有大文件解析交给 chayuan-desktop sidecar。加载项侧只是 触发解析 + 显示进度。

大文件解析的内存控制是 chayuan-desktop 单机版的工程基础。免费开源的AI软件 想覆盖政企客户的真实场景，必须扛得住几百兆甚至几个 G 的文档。chayuan-desktop 在这一面做了系统性的工作。
