# 嵌入模型升级要不要重建 老索引兼容的边界

chayuan-desktop 桌面单机版升级时偶尔会涉及嵌入模型的版本变化。比如 bge-m3 v1.0 升级到 v1.1，或者从 bge-m3 换到 bge-m4。这种变化时老索引怎么处理是工程上的实际问题。这一篇讲清楚兼容边界。

先看嵌入模型的变化分几种。

类型一：完全相同模型。chayuan-desktop 升级时模型没动。老索引完全可用，没事。

类型二：同模型小版本升级。比如 bge-m3-onnx 从 v1.0.0 升到 v1.0.1（修了几个 bug）。模型权重没大改，向量分布几乎相同。chayuan-desktop 默认认为兼容，不强制重建。检索精度可能微小变化。

类型三：同模型大版本升级。比如 bge-m3 从 v1.0 升到 v1.1（训练数据更新或者结构调整）。向量分布有差异但维度相同。chayuan-desktop 给出提示 建议重建索引以达到最佳精度，用户决定。

类型四：换模型。比如 bge-m3 换 bce-embedding。向量空间完全不同，不可能兼容。chayuan-desktop 必须重建。

类型五：维度变化。比如 1024 维换 768 维。索引文件结构都不一样，必须重建。

chayuan-desktop 的 KB 元数据里记录什么。每个 KB 记录建库时使用的 embedding_model_name 和 embedding_model_version 字段。检索时按这两个字段决定用哪个模型给 query 嵌入。

升级流程。chayuan-desktop 装新版本启动后做几件事。第一，检查所有 KB 的 embedding_model 元数据。第二，跟新版本支持的模型列表对比。第三，按情况标记 KB 状态。

KB 状态。compatible：老 KB 跟新版本兼容，正常工作。warn：建议重建索引但能用。incompatible：必须重建才能用。

前端展示。compatible 的 KB 没变化。warn 的 KB 在 KB 详情页显示 黄色感叹号 + 建议升级索引。incompatible 的 KB 显示 红色警告 + 必须重建。

强制兼容模式。某些用户有大 KB（百万 chunk）重建成本高，想继续用老索引。chayuan-desktop 提供 强制兼容 开关，KB 仍然能查询，但检索精度可能不如重建后的。这种 让用户自己取舍 的设计务实。

模型权重的存储。CHAYUAN_ROOT/models 目录下每个模型权重在自己版本子目录。比如 embeddings/bge-m3-onnx/v1.0/ 和 embeddings/bge-m3-onnx/v1.1/ 共存。chayuan-desktop 升级时下载新版本到新子目录，老 KB 仍能用老权重。

权重的清理。如果某个老版本权重不再被任何 KB 使用（用户已经全部重建），chayuan-desktop 提供 清理未用模型 工具释放磁盘。

升级提示的时机。chayuan-desktop 升级到新版本第一次启动时弹窗 检测到模型升级机会，X 个 KB 建议重建索引，给用户 立即重建 / 稍后处理 / 不再提示 三个选项。立即重建会把所有 KB 排队重建（后台跑）。

部分重建。chayuan-desktop 当前不支持 KB 内部分重建（只重建变化的 chunk），重建是全 KB 操作。这是 sqlite-vec 索引结构的限制。

跨 KB 嵌入模型的混合。一台 chayuan-desktop 上不同 KB 用不同嵌入模型完全可以。chayuan-desktop 在多 KB 并联检索时按每个 KB 的 embedding_model 给 query 单独算嵌入。同一个 query 可能算两次嵌入，对延迟影响可控（毫秒级）。

国产化支持下的模型升级。智源、网易、阿里这些国产嵌入模型的升级节奏跟海外不同步。chayuan-desktop 跟踪几家主要国产嵌入模型的版本，提供官方支持的稳定版本。用户也可以在设置里指定具体版本。

外部向量库的嵌入模型管理。src:* 类型的 KB（比如 Milvus）的嵌入模型由用户在外部建库时决定。chayuan-desktop 这边只在连接配置里记录 embedding_model 字段。如果外部 collection 升级了模型，用户在 chayuan-desktop 里更新连接配置即可。

WPS AI 插件 chayuan-wps 不感知嵌入模型版本。加载项通过 sidecar 检索，sidecar 自动用对应模型。这种透明性让加载项跟模型升级解耦。

嵌入模型升级要不要重建是 chayuan-desktop 的运维判断。免费开源的AI软件 让用户在 维持兼容 和 追求精度 之间自己选择，是务实的工程态度。
