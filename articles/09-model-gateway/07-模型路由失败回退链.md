# 模型路由失败的回退链 fallback 链路设计

chayuan-desktop 桌面单机版的模型网关在某个模型调用失败时自动回退到下一个可用模型。这一篇讲 fallback 链路设计。

## 失败场景

场景一。OpenAI Key 配额用完。429 限速错误。

场景二。厂商 API 临时故障。500 / 502。

场景三。网络不通。timeout。

场景四。模型下线。404 model not found。

场景五。账号被风控。403 access denied。

每种失败都该有应对。

## fallback 链路定义

用户在 chayuan-desktop 设置里给每个类别配 fallback 链。

```
chat fallback chain:
  1. gpt-4o (openai)
  2. claude-3.5-sonnet (anthropic)
  3. qwen-plus (dashscope)
  4. ollama:qwen2.5:7b (本地)
```

主用 gpt-4o。失败按顺序回退。最终回退到本机 Ollama 兜底。即使全部线上失败也能给个答案。

## 自动判定失败

chayuan-desktop 的网关识别这些状态作为 失败。

HTTP 4xx 中的 401 / 403 / 404 / 429 视为失败。

HTTP 5xx 全部视为失败。

网络层 timeout / connect refused 视为失败。

LLM 返回流但中途断开，content 为空，视为失败。

业务层错误（content 含 抱歉，我无法回答）不算 失败，是模型行为不是路由问题。

## 回退的代价

回退会让 单次请求 走多个模型，增加总延迟。

chayuan-desktop 限制总尝试次数。默认每次请求最多尝试 3 个模型（主 + 2 个 fallback）。超过这个限制直接返回错误给用户。

避免无限等待。

## 流式场景的 fallback

流式请求的 fallback 复杂。如果主模型已开始流出 token，中途断开，fallback 能从头开始还是续接。

chayuan-desktop 的策略。如果主模型在 1 秒内没开始流出 token 就 fallback。如果已经流出 token 中断，告知用户 主模型中断，重新生成中 然后从头跑 fallback。

不让用户看到混合两个模型输出。语义不连贯。

## 用户感知

UI 上显示 fallback 状态。某次回答的引用气泡或元信息标 由 claude-3.5-sonnet 生成（gpt-4o 限速回退）。让用户知道实际用的哪个。

不强制提示。低调显示在 hover 卡片里。

## fallback 的开销限制

某些用户配了昂贵的 fallback 链（比如 GPT-4 → Claude-Opus → Gemini-Ultra）。一次请求三个高价模型可能用户没意识到。

chayuan-desktop 设置里有 fallback 的 成本上限。预估单次 fallback 链总成本超过阈值时不自动回退，问用户 是否换便宜模型重试。

## 临时下线的处理

某个模型连续失败 N 次，chayuan-desktop 临时把它从 fallback 链里剔除（30 分钟）。避免每次请求都先尝试已经死的模型浪费时间。

30 分钟后自动恢复重试。

## 国产化场景

政企用户希望主用国产模型，国外模型作 fallback（避免被卡脖子）。chayuan-desktop 的 fallback 链让用户灵活配置。也支持 全国产链 配置（文心 → 通义 → 智谱 → Qwen-本地），完全不依赖国外。

## chayuan-server 协同

chayuan-server 多用户场景下 fallback 链可以企业级配置。chayuan-desktop 单机版用户级配置。

## WPS 加载项

chayuan-wps 在 WPS 里发起调用走 chayuan-desktop 网关。fallback 对 WPS 透明。WPS 里看到的就是 网关给的最终答案，不知道经历了几次 fallback。

## 总结

模型路由失败的 fallback 链是 chayuan-desktop 在工程鲁棒性上的设计。免费开源的AI软件 接入多厂商必须考虑单点失败问题。chayuan-desktop 的 fallback 链 + 时间限制 + 成本上限 + 临时剔除 让模型路由在工程上稳。
