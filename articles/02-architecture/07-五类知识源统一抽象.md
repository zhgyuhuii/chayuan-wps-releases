# 本地离线知识库不只是一种 KnowledgeRef统一抽象的设计动机

chayuan-desktop 桌面单机版有一个 五类知识源 的说法：文档库、结构化数据库、向量库、办公私库、外部连接器。这五种东西从形态到用途都不一样，但在察元AI 的内部接口里它们被统一成一种叫 KnowledgeRef 的抽象。这一篇讲这个抽象是怎么设计出来的，为什么这么做。

先看五类知识源各自的特征。文档库（doc）保存的是 PDF/Word/Excel/PPT 等切分后的 chunk，配 bge-m3 嵌入做向量召回。结构化数据库（src 类型之一）保存的是 SQL 表，问答走 text2sql 链路。向量库（src 类型之一）保存的是外部 collection 里的向量加 metadata，问答走 ANN 检索。办公私库（office）保存的是私人或团队级别的资料，按 owner:group 分隔。外部连接器（src 类型）覆盖 Milvus、Chroma、Elasticsearch、达梦、金仓等十几种异构源。

如果不做统一抽象。每个上层调用都要 if-else 判断当前请求要查哪种源，然后分别调对应的 API。前端要为每种源写不同的 UI 组件展示。回答里的引用要按源类型分别处理。代码膨胀得很快，新增一种源就要改一遍上层代码。

统一抽象 KnowledgeRef 怎么设计。每个知识源被抽象成一个 KnowledgeRef，结构包括：ku_id（唯一标识，格式 doc:* / src:* / office:*）、kind（doc / structured / vector / office / web）、display_name（展示名）、metadata（元数据）。前端只持有 ku_id 和 kind 两个核心字段，所有路由按 ku_id 解析后归到对应 adapter。

ku_id 的命名空间。doc:文档库名 是默认文档 KB，比如 doc:技术资料 doc:合同档案。src:外部源 ID 是外部连接器，比如 src:milvus_local src:dm_finance。office:owner[:group] 是办公私库，比如 office:zhangsan office:zhangsan:team_a。三种命名空间互不冲突，前端展示时按 kind 字段渲染图标和说明。

设计的几个动机。第一动机是 前端持有真源。如果前端只持有 显示名，把 显示名 当成 KB 名往后端发，会出现重名 KB 不知道点哪个的歧义；持有 ku_id 之后不会有这个问题。第二动机是 路由统一。后端拿到 ku_id 一看就知道走哪个 adapter，不用再回查 KB 类型。第三动机是 演进友好。新增源类型只需要扩 ku_id 命名空间，老接口不变。

不要把 src:* 当作普通文档 KB 处理。这是一条架构红线。早期某些版本里前端会把外部源混进 kb_names 字段，结果后端把外部源当文档库走，跑出来全是错的检索。新版本的合同明确要求前端用 ku_ids 携带所有源，kb_names 只作为旧文档 KB 的兼容字段。这个细节 CLAUDE.md 里写得很清楚。

KnowledgeRef 的 metadata 字段。不同 kind 的源在 metadata 里携带不同字段。文档库会有 chunk 数量、嵌入模型、最近一次同步时间；结构化库会有数据库连接信息（脱敏）、表数量、白名单状态；向量库会有 collection 数量、维度、距离度量；办公私库会有 owner、group、密级。这些 metadata 不影响检索逻辑，主要给前端展示用。

KnowledgeRef 与 RetrievalHit Citation Diagnostic 的对应关系。一次检索请求带一组 KnowledgeRef 进入 orchestrator，每个 KnowledgeRef 派给对应 adapter 跑出一组 RetrievalHit。RetrievalHit 里携带 ku_id 来源、score、内容片段、metadata。Citation 是 RetrievalHit 的展示形态，前端基于 kind 渲染不同 UI。Diagnostic 是 adapter 跑过程的诊断信息，比如 SQL、向量距离、命中规则。

引用展示的差异。doc 来源的引用气泡可以展开原文段落、跳转到 PDF 页码；structured 来源的引用展示 SQL、表、行；vector 来源的引用展示 collection、vector id、metadata；office 来源的引用展示文件路径、owner、group。同一组接口出来的结果，前端按 kind 分流渲染，体验对用户一致但细节不同。

下载按钮的特别处理。doc 来源的 chunk 有原文件，可以提供下载按钮。vector 来源的命中通常没有原文件，下载按钮不能开。这是 KnowledgeRef 抽象在 UI 层的实际影响：用户不会被一个 下载 按钮误导成所有命中都有完整文档可下载。

WPS AI 插件 chayuan-wps 完全基于 ku_ids 与 KnowledgeRef 工作。加载项里展示的 KB 选择器、引用气泡、检索编排，跟桌面客户端共用同一套抽象。这套统一保证了在 WPS 文字里使用察元智库 跟在桌面客户端使用是同一种体验。

KnowledgeRef 这一层抽象做对了，五类知识源 这件事才能持续扩展。新增一种源类型只是新增一个 adapter 加一个 ku_id 命名空间，不动任何已有代码。免费开源的AI软件 的可演进性很大程度上来自这种核心抽象的稳定。
