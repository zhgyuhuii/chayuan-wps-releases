# 多Tab并行对话 资源隔离与共享的边界

chayuan-desktop 桌面单机版的对话区是浏览器式 Tab 设计：你可以同时开五六个对话 Tab，每个跑不同模型问不同 KB，互相不干扰。这种 Tab 并行 看上去像浏览器多标签，背后的资源管理跟浏览器其实有些不同。这一篇讲清楚 Tab 并行的资源隔离边界。

先看 Tab 在前端的状态结构。每个 Tab 有自己的对话 ID、消息列表、当前流式状态、用户输入草稿、选中的模型、勾选的 KB 列表。这一组状态在 React 应用内存里独立维护，前端不共享。Tab 切换不会清理另一个 Tab 的状态。

后端的处理。每个 Tab 发起的请求是独立的 HTTP 调用，sidecar 视为各自独立的对话。同一时刻可能有多个 Tab 在同时跑流式响应，sidecar 的 FastAPI 用 asyncio 异步处理，每个请求一个协程。

资源边界一：模型供应商。所有 Tab 共享同一份模型供应商配置。改一个供应商的钥匙会影响所有 Tab。这种共享的好处是不需要每个 Tab 都重配。

资源边界二：模型并发。某些厂商对单 Key 有 RPM（每分钟请求数）限制。多个 Tab 同时请求同一厂商，可能命中限速。chayuan-desktop 的网关层会做请求排队和退避，避免触发厂商封号。如果排队让用户等太久，前端给出 当前厂商繁忙 的提示。

资源边界三：本地推理。如果你接的是 Ollama 或 vLLM 跑本地推理，本地 GPU 资源有限。多个 Tab 同时请求会在 Ollama 内部排队。Ollama 默认有自己的并发窗口，超出的请求等待。chayuan-desktop 不替 Ollama 做更细的调度，遵从本地推理服务的能力。

资源边界四：知识库检索。多个 Tab 同时检索同一个 KB 没问题，sqlite-vec 在 WAL 模式下支持并发读。检索同一份大模型嵌入也没问题，bge-m3-onnx 在 CPU 上是线程安全的。但是如果两个 Tab 同时往同一 KB 写入（比如同时拖文件进库），sidecar 会内部串行化避免 SQLite 写冲突。

资源边界五：流式响应。每个 Tab 的 SSE 连接是独立的，互相不影响。但 chayuan-desktop sidecar 单进程，所有流式响应共用一个事件循环。极端情况下（几十个 Tab 同时流式），事件循环会有阻塞风险。日常使用 5-10 个 Tab 没问题。

资源边界六：内存占用。每个 Tab 在前端占用大约几十 MB 内存，对话历史长的会更多。后端不为每个 Tab 单独分配内存，只在请求处理时占用。所以 Tab 数量在前端是主要瓶颈，几十个 Tab 之后 webview 会变慢。

Tab 拖拽与上下文菜单。chayuan-desktop 支持 Tab 拖拽改顺序、右键关闭、关闭其他、关闭全部。这些 UI 行为不影响后端，只是前端状态调整。

历史 Tab 的恢复。chayuan-desktop 关闭再打开时，前端会恢复上次的 Tab 列表（对话 ID 列表），点哪个 Tab 才真的把对话历史从 SQLite 拉回。这种 lazy 加载让启动快，避免恢复时一次拉太多对话造成卡顿。

跨 Tab 的共享状态。模型供应商配置、KB 列表、设置项是全局的，改一处所有 Tab 看到。当前选中的模型和 KB 是 Tab 级的，每个 Tab 独立。这种切分让用户可以在一个 Tab 用 GPT 一个 Tab 用 DeepSeek，互不干扰。

并发 Tab 的实际场景。一是模型对比，但更专门的方式是用 模型对抗 arena。二是不同主题对话同时开，比如一个 Tab 写报告一个 Tab 查代码。三是不同 KB 并行查询，每个 Tab 选不同的 KB 组合。

Tab 关闭的清理。关闭 Tab 不会删对话历史，对话仍在历史列表里随时可以打开。如果你想真删除，需要从历史列表里右键 删除对话。这个细节避免了误关 Tab 丢对话。

国产化支持下的特别注意。麒麟桌面 V10 上 webview 对多 Tab 的渲染性能略低，建议同时开的 Tab 不超过 8 个。loongarch64 平台同样，单进程 webview 的能力有限。

WPS AI 插件 chayuan-wps 在加载项里没有 Tab 概念，每次问答是独立请求。但加载项跟 chayuan-desktop 共用 sidecar，加载项发起的请求跟桌面客户端的 Tab 是平等的，sidecar 视为不同 HTTP 连接。

多 Tab 并行这件事看起来普通，背后的资源管理对单机版来说挺关键。免费开源的AI软件 想做出 像浏览器那样自然 的并行体验，前端状态、后端并发、外部依赖三层资源都要打磨。
