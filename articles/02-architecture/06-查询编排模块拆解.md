# 本地离线知识库的查询编排 retrieval/query 模块拆解

chayuan-desktop 后端 sidecar 里有一个核心模块叫 retrieval/query，负责把用户的一句问话变成对多个知识源的并发检索任务，再把结果聚合回来。这个模块是 察元智库 能同时查文档、结构化、向量、办公库的那一份内部机器。这一篇拆开看里面长什么样。

模块按职责分成几个子模块：refs、authz、router、orchestrator、adapters、results。这套切分是 CLAUDE.md 里写过的架构原则的具体落地。每个子模块只做一件事，路由文件只做协议适配。

refs 子模块负责解析 ku_ids。ku_id 是 chayuan-desktop 里 知识源的唯一标识，格式是 doc:文档库名、src:外部源 ID、office:owner:group 这三种。refs 模块把请求里的 ku_ids 列表拆开来，对每个 id 查询元数据：这个库属于谁、是什么类型、当前可不可用、需要什么权限。解析失败的 id 会返回结构化的错误，告诉上层是格式不对还是库不存在。

authz 子模块负责权限判断。单机版默认关鉴权，所以这一层在单机模式下基本是直通的，所有请求都视为合法。但在多用户版本和企业版本里这一层会校验当前用户是不是能访问对应的 KB。统一的 authz 层让 chayuan-desktop 可以从单机模式平滑过渡到多用户模式而不改业务代码。

router 子模块负责识别查询意图。它根据问题的特征判断走哪种检索策略：document_qa（文档问答）、structured_aggregate（结构化聚合）、structured_lookup（结构化查找）、vector_semantic（向量语义检索）、multi_source（多源混合）。判定逻辑结合了模型分类和规则启发，比如 有几个用户 这种问题会自动识别为 structured_aggregate 并走 SQL 路径，不会退化到文档 chunk 检索。

orchestrator 子模块负责并发调度。一次问答可能涉及多个 KB，orchestrator 把每个 KB 上的检索任务派给对应的 adapter，按超时和并发上限做编排。任意一个 adapter 失败不会拖累整体。orchestrator 会维护 trace（每一步耗时、错误、命中数），最终把成功的结果聚合，失败的诊断信息也带回去。

adapters 子模块按源类型实现具体检索。document adapter 负责文档库的向量召回加重排；structured adapter 负责 SQL 生成、AST 校验、执行、结果验证；vector adapter 负责外部向量库的 collection 查询；office adapter 负责办公私库的命名空间检索。每个 adapter 暴露同一组接口：search、explain、citations。

results 子模块负责输出格式化。把所有 adapter 的返回值统一成 QueryBlock 数据结构，每个 block 含 RetrievalHit（命中片段）、Citation（引用元数据）、Diagnostic（诊断信息）。前端拿到的就是这种统一结构，渲染引用气泡、诊断卡片、源类型分类都基于此。

路由文件不放业务逻辑。/api/v1/kb-query/search 这个 HTTP 路由在 api_server 目录下，只做协议适配：解析请求体、做参数校验、注入身份、调 service.kb_query 函数。所有的 refs、authz、router、orchestrator、adapters、results 这一套都在 service 层和 retrieval/query 层。这种切分让路由代码非常干净，几十行就够，业务逻辑在专用模块里。

为什么这么切。两个原因。一是可测试性。每个子模块独立可单元测试，refs 解析、router 判定、adapter 调用、results 聚合都可以单独 mock。chayuan-server 的 tests 目录里这一类合同测试有上百条。二是可演进。新增源类型只需要写一个新 adapter，不用改 router 和 orchestrator。新增意图类型只需要扩展 router，不用改 adapters。

实际跑一次问答的时序。用户在前端发 你这个 KB 里关于压力测试的内容总结一下，sidecar 路由到 kb_query.service。service 拿到 ku_ids（前端选的那几个 KB），调 refs 解析；调 authz 校验；调 router 判定意图（document_qa）；调 orchestrator 派发任务；orchestrator 选 document adapter 跑向量召回加重排；adapter 返回 RetrievalHit 列表；results 聚合成 QueryBlock；service 把结果加上 LLM 生成的回答返回给前端。整个过程毫秒到秒级。

国产化支持下的特殊点。结构化 adapter 对国产数据库（达梦、金仓、Doris）的方言处理在 structured_tools 模块里有专门的方言适配。SQL 生成时会带方言标记，AST 校验时按方言规则走。

WPS AI 插件 chayuan-wps 通过 /api/v1/kb-query/search 接口调用同一套查询编排。加载项里调起的检索跟桌面客户端走的是同一份 retrieval/query 模块，结果格式、引用气泡、诊断信息完全一致。

模块化设计的好处在维护时最明显。每次新增功能或修 bug 都能快速定位到对应子模块，不会出现一个改动到处影响的情况。免费开源的AI软件 想长期维护，这种内部架构的清爽程度直接决定后期能不能持续迭代。
