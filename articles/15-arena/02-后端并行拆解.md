# 模型对抗的运行时拆解 后端怎么并行

chayuan-desktop 桌面单机版的模型对抗多模型并行回答，背后是怎么实现的。这一篇讲清楚。

请求流程。

第一步。用户在 arena 界面点 统一发送。前端把 query 跟参与对抗的模型列表打包发给 sidecar。

第二步。sidecar 收到请求，对每个模型并发起一个独立的对话任务。

第三步。每个任务调对应模型 adapter 发请求给厂商。

第四步。每个任务收到流式响应（SSE），通过独立 channel 推回前端。

第五步。前端按 task_id 把每个流式事件路由到对应泳道渲染。

并发模型。Python asyncio.gather 起 N 个 task 并发跑。每个 task 内部是 httpx.AsyncClient 异步 HTTP 调用。N 个泳道几乎完美并行（CPU 不是瓶颈，IO 等待并发即可）。

资源限制。

资源一：厂商 RPM 限速。同一厂商多个泳道（比如对比 GPT-4o 和 GPT-4-turbo，都属 OpenAI），共享 RPM 限制。chayuan-desktop 的限速 pool 给同厂商的请求排队。

资源二：本地推理。如果某个泳道是本地 Ollama，本地 Ollama 内部串行处理。第二个本地泳道要等。这种 本地是隐性串行 在 arena 场景里要注意。

资源三：网络带宽。多个泳道并发流式，网络带宽消耗大。

延迟。整体延迟接近最慢的那个泳道（其他都更快完成）。陈述慢的模型拖累整体感知。

错误隔离。某个泳道失败（厂商限速、模型不可用）显示该泳道红色，其他泳道照常完成。

成本累计。多个泳道独立调厂商 API，成本是各家累加。chayuan-desktop 在前端显示总成本。

实现细节。

细节一：每泳道独立 conversation。chayuan-desktop 给每个对抗泳道生成独立 conversation_id，对话历史不互相污染。

细节二：每泳道可以手动延续。对抗结束后用户可以选某个泳道 转入正式对话，把那一组对话历史保留下来。

细节三：取消对抗。用户中途想停掉。点一个 取消，chayuan-desktop 给所有泳道发 abort 信号，正在跑的请求被打断。

细节四：可观测。每泳道的延迟、tokens/s 等数据实时显示。

国产化支持下的并行。混选国产 vs 海外厂商一起跑没问题。chayuan-desktop 的 adapter 抹平协议差异。

WPS AI 插件 chayuan-wps 当前不支持对抗。只在桌面客户端。

模型对抗的并行实现是 chayuan-desktop 工程上的细节工作。免费开源的AI软件 让多模型对比变 可视、可量化、可重复，靠的是这种并行架构。chayuan-desktop 的 arena 是 全模型支持 的实战体现。
