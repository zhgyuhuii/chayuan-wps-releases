# 结构化KB的访问审计 每条SQL都留痕

chayuan-desktop 桌面单机版对结构化 KB 的所有访问都留审计日志。这一篇讲审计日志的设计和用途。

先看为什么要审计。

理由一：合规。等保 2.0、政企信创要求所有数据访问可追溯。LLM 跑了什么 SQL、谁让它跑、什么时候跑、结果是什么，都要记录。

理由二：故障回放。出问题时能回看当时跑了什么。

理由三：异常检测。频繁失败的 SQL、大数据扫描可能是攻击或系统问题。

理由四：用量统计。哪些 KB 用得多、哪些字段被频繁查、哪些用户活跃。

审计日志的字段。chayuan-desktop 的 audit_log 表记录这些。

第一组：身份。user_id（单机版下 system 或 OS 用户）、session_id、source（web/wps）。

第二组：时间。请求时间戳。

第三组：内容。query 原文、识别的意图、生成的 SQL、命中的 KB、用到的表和字段。

第四组：执行。SQL 执行时间、影响行数、是否成功。

第五组：结果。返回字段（脱敏后）、数据规模。

第六组：元数据。trace_id（关联 LLM trace）、ip 地址（多人后端时）、user_agent。

审计日志的存储。SQLite 表（chayuan.db audit_log）。每条记录大约 1-5KB。一个用户日常使用一个月可能积累几万条记录。SQLite 完全扛得住。

审计日志的查询。chayuan-desktop 提供 设置 - 审计 界面，按时间、KB、用户、SQL 模式查询。常用查询。

谁今天访问了 src:dm_finance KB。

最近一周失败的 SQL 列表。

某个 SQL 模式最近被跑了多少次。

某个时间段内的所有访问。

审计日志的导出。chayuan-desktop 支持把审计日志导出 CSV 或 JSON，方便提交合规报告。导出时按需脱敏（敏感数据值 mask）。

审计日志的保留期。默认 365 天。等保 2.0 要求至少 6 个月，多数客户要求 1 年。chayuan-desktop 默认满足主流合规要求。

审计日志的脱敏。SQL 里可能含敏感参数（用户身份证号、银行卡号）。chayuan-desktop 的审计日志默认对参数值做 mask 处理（留前 3 位 + 后 4 位，中间 ***）。

审计日志的不可篡改。某些场景要求审计日志不能被修改（即使管理员也不能）。chayuan-desktop 当前是普通 SQLite 写入，理论上能改。企业版可以集成 WORM（write-once-read-many）存储，让审计真正不可篡改。

审计日志的发送。某些客户希望审计日志同步发送到 SIEM（安全信息事件管理）系统。chayuan-desktop 支持配置 syslog 或 webhook 把每条审计同步发出。

审计日志的差异化。不同操作的审计级别不同。

读操作（SELECT）：simple 级别，记录 SQL + 时间 + 行数。

写操作：chayuan-desktop 默认拒绝写操作，但如果用户开启了写权限，就 detailed 级别记录每次写入。

DDL 操作：拒绝。

模型调用：记录哪个模型被调用、token 数量。

工具调用：记录哪个工具被调用、参数（脱敏）。

实际审计场景。

场景一：合规审计。监管机构来查 LLM 跑了哪些 SQL。chayuan-desktop 的审计日志直接出报告。

场景二：性能调优。某个 KB 慢查询多。审计日志统计 哪些 SQL 模式占用 80% 的执行时间，DBA 加索引优化。

场景三：使用统计。给老板做月度报告 LLM 帮员工查了多少次。审计日志按 query count 统计。

场景四：异常检测。某天 query 突然激增。审计日志按时间段统计，定位异常时段和 query 模式。

国产化支持下的审计。等保 2.0 三级以上要求审计完整。chayuan-desktop 的审计日志覆盖等保的所有 必记事件。具体合规对接看客户单位的等保实施方案。

WPS AI 插件 chayuan-wps 发起的查询同样被审计。审计日志的 source 字段标记 wps，跟桌面客户端的 web 区分。

访问审计是 chayuan-desktop 在政企场景立足的合规底盘。免费开源的AI软件 想真服务政企，审计能力是基本素质。chayuan-desktop 在这一面的工程化让 真合规可用 这件事成立。
