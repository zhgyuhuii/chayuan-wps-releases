# 大表慢查询的应对 LIMIT与执行超时

chayuan-desktop 桌面单机版的 text2sql 在小表上查询飞快，但在大表（千万行以上）上偶尔慢。这种慢可能让 sidecar 卡住或者用户等急。这一篇讲应对策略。

先看慢查询的几种典型原因。

原因一：缺索引。WHERE 条件涉及的字段没建索引，数据库做全表扫描。

原因二：关联表大。多表 JOIN，每张几百万行，笛卡尔积大。

原因三：聚合数据量大。GROUP BY 字段值很多，聚合中间结果大。

原因四：WHERE 条件太宽。比如 SELECT * FROM logs（几亿行）没条件。

chayuan-desktop 的策略。

策略一：强制 LIMIT。AST 校验阶段如果 SQL 没 LIMIT，自动加 LIMIT 100。这是兜底。万一 LLM 生成 SELECT * FROM huge_table 不至于让数据库炸。

策略二：执行超时。每条 SQL 默认 30 秒超时。超过的话 chayuan-desktop 主动 cancel 查询，给用户错误：查询超时，建议优化条件。这避免长慢查询拖累整个 sidecar。

策略三：估计扫描规模。chayuan-desktop 在执行 SQL 前可以跑 EXPLAIN（PG/MySQL 等支持），看预期扫描行数。如果超过阈值（比如 1000 万行），警告用户 这个查询可能很慢。

策略四：建议索引。如果用户反复跑同一个慢 SQL，chayuan-desktop 的诊断里建议 该字段建议加索引。这是给 DBA 的提示，chayuan-desktop 不主动改 schema。

策略五：拒绝危险 SQL。某些明显的危险 SQL（SELECT * 没 WHERE 在大表上），AST 校验阶段直接拒绝，让 LLM 重新生成更具体的 query。

具体实例。

实例一：全表扫描。LLM 生成 SELECT * FROM orders WHERE region='华南'。如果 region 没索引且 orders 是 5000 万行，扫描慢。chayuan-desktop 在 EXPLAIN 后给警告。

实例二：超时。慢 SQL 跑 30 秒没出，超时取消。给用户的错误：当前查询执行时间超出 30 秒限制，可能数据量过大。建议先用 LIMIT 看部分结果，或者加更具体的 WHERE 条件。

实例三：JOIN 笛卡尔积。LLM 写 SELECT * FROM A, B（缺 JOIN ON）。这种笔误产出几百亿行。chayuan-desktop 的 AST 校验识别 cross join 模式（缺 JOIN ON），警告 这看起来是笛卡尔积，确认是否真要这样。

实例四：聚合中间结果。GROUP BY 一个高基数字段（比如 user_id 几百万种值）。聚合中间结果占内存。chayuan-desktop 给出建议：考虑加 LIMIT 或者按时间分组。

LLM 的优化提示。chayuan-desktop 的 prompt 给 LLM 几条优化建议。

建议一：先 LIMIT 100 试试。

建议二：WHERE 条件越具体越好。

建议三：避免 SELECT *，明确字段列表。

建议四：聚合时考虑时间窗口。

LLM 跟着提示能写出更优雅的 SQL。

数据库本身的优化。chayuan-desktop 不接管数据库优化，但建议用户。

DBA 配合。给频繁查询的字段加索引。partition 大表（按时间或 ID 分区）。设置 query plan 统计更新频率。

chayuan-desktop 配合。配置查询超时阈值。配置默认 LIMIT 大小。配置 危险 SQL 拒绝规则。

用户配合。问问题时尽量明确（哪个时间段、哪个地区、什么条件）。避免 全公司所有数据 这种宽泛 query。

国产化支持下的慢查询。达梦 DM、金仓 KingbaseES 在大表上的性能跟商业 PG 接近。Doris ClickHouse 强于聚合查询。慢查询应对策略相同。

WPS AI 插件 chayuan-wps 在 WPS 里跑慢 SQL 时同样受超时保护。慢 SQL 不会让 WPS 加载项卡死。

大表慢查询是 chayuan-desktop 在生产场景下的实际挑战。免费开源的AI软件 想让 text2sql 在企业级数据库上可用，慢查询的策略性应对是必要工作。chayuan-desktop 在这一面的工程细节让 真生产数据 也能放心接入。
