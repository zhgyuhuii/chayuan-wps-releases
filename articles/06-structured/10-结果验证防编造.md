# 结果验证 LLM不能编答案的具体兜底

chayuan-desktop 桌面单机版的 text2sql 流程里有一道用户看不到但很重要的步骤：结果验证。LLM 生成 SQL 跑出结果之后不直接给用户，先做几项验证，确认结果合理再让 LLM 总结成自然语言。这一篇讲清楚结果验证做什么。

先看为什么要验证。LLM 写 SQL 不是百分百正确，可能字段错、条件错、表错。SQL 跑出来一个 0 或者一个空集，LLM 在总结时可能 编一个数字 或者 说 没找到数据。两种情况都让用户被误导。结果验证在这两者之间做出判断。

验证项一：SQL 真的执行成功。如果 SQL 报语法错或权限错，结果验证识别这是 失败，给用户明确错误：SQL 执行失败，原因 X。不让 LLM 跳过这个错误编一个答案。

验证项二：结果集大小合理。

零行结果。不一定错（可能确实没匹配数据）。但要验证是 数据真没有 还是 SQL 有 bug。chayuan-desktop 检查 WHERE 条件是不是过严。比如 WHERE date >= '2027-01-01' 在 2026 年的数据库上当然零行，提示用户 时间条件超出数据范围。

超大行数。SELECT * FROM huge_table 没 LIMIT 返回几百万行。chayuan-desktop 的 AST 校验阶段已经强制加 LIMIT，但万一 LIMIT 100 仍嫌多，结果验证会截断展示给 LLM 的部分。

合理范围。某些查询有 业务上的合理范围。比如 一年内的总销售额 不可能是负数。chayuan-desktop 不做硬编码业务规则，但极端不合理结果（负数计数、超大数字）会标记 异常 让 LLM 注意。

验证项三：字段类型对。SELECT SUM(amount) 期望返回 numeric，但实际返回 string（amount 字段类型是 text）。这种类型问题让 LLM 知道 SQL 的语义可能错了。

验证项四：跨字段一致性。某些情况下结果里多列必须一致（行数 + sum_amount 这种）。如果 sum_amount 是 NULL 但 行数 大于 0，可能是某些字段缺失值，提示用户。

LLM 总结的约束。结果验证完成后，LLM 拿到的是 验证后的结果。chayuan-desktop 给 LLM 的 prompt 里强制一条：你必须基于查询返回的实际数据回答，不允许编造数字。如果数据不足以回答，告诉用户 数据中没有相关信息。

验证失败的处理。结果验证失败时不让 LLM 编答案，给用户的是结构化错误：

错误一：SQL 执行失败。原因 X，建议 Y。

错误二：结果集为空。可能原因 X，建议调整 query 或检查数据范围。

错误三：结果异常。具体异常 X。

LLM 在错误情况下不参与回答，避免编造。

可信度信号。结果验证给每次结构化查询打一个 confidence score：执行成功 + 数据合理 = high。执行成功但结果异常 = medium。执行失败 = low。前端按 confidence 展示对应的视觉标记（绿/黄/红）。

验证在跨问题流程里的位置。chayuan-desktop 的对话流程是：用户问 → router 识别意图 → text2sql 生成 → AST 校验 → 执行 → 结果验证 → LLM 总结 → 返回前端。结果验证在执行和总结之间，是关键关卡。

CLAUDE.md 里的硬要求。结构化数据问题不能让 LLM 编答案，必须基于真实数据。结果验证是这条要求的具体执行。

LLM 的训练数据偏差。某些 LLM 在训练时见过 类似场景的数字，可能在没数据时偷偷凭印象编。chayuan-desktop 的 prompt 严格防止这种行为：你只能基于本次查询返回的数据，不许引用任何外部知识。

跨方言的验证。不同数据库返回值格式略有差异（PG 的 numeric 跟 MySQL 的 decimal）。chayuan-desktop 的验证层归一化处理，统一成 Python 类型给 LLM。

国产化支持下的验证。达梦、金仓的查询结果跟 PG 一致格式。结果验证逻辑通用。

WPS AI 插件 chayuan-wps 在 WPS 里跑结构化查询同样走结果验证。如果验证失败，加载项给用户清晰的错误信息，不会让 LLM 编答案误导用户在报告里写错数字。

结果验证是 chayuan-desktop text2sql 链路的最后一道防线。免费开源的AI软件 想让用户在生产环境敢用 AI 算数据，结果可信度必须保证。chayuan-desktop 在这一道关卡上的工程化让 数字答案 真的可信。
