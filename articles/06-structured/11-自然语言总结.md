# 全模型支持下的自然语言总结 在SQL跑完之后再讲故事

chayuan-desktop 桌面单机版的 text2sql 流程的最后一步是让 LLM 把 SQL 结果转成自然语言。这一步看着简单实则有几个细节。这一篇讲清楚。

先看为什么要 LLM 总结。SQL 结果是一行数字 1234567 或者一张 12 行的表格。直接展示不友好。让 LLM 把它包装成 上个月华南地区的销售总额是 123 万元 这种自然句子，用户体验好。

LLM 总结的输入。chayuan-desktop 给 LLM 的 prompt 包括：原始 query（用户问什么）、生成的 SQL（怎么查的）、SQL 结果（实际数据）、表 schema（字段含义）、可选的 context（其他相关信息）。LLM 基于这些写一段中文回答。

总结的几个原则。

原则一：基于事实，不编造。LLM 必须用查询返回的真实数据，不允许引用训练知识。chayuan-desktop 的 prompt 强调这条。

原则二：自然流畅。不能机械地说 查询结果是 123。要说 上个月华南地区销售总额约 123 万元，比之前增长 X%（如果有对比信息）。

原则三：精度保留。数字不要随意取整或四舍五入。LLM 倾向把 1234567 写成 大约 100 万，这种简化可能造成误读。chayuan-desktop 的 prompt 要求 LLM 保留原始精度，需要简化时明确说明 约 X 万。

原则四：单位明确。如果数据有单位（元、kg、件），LLM 必须带上。某些字段单位在 schema 注释里有，prompt 把它一起给 LLM。

原则五：上下文关联。如果 query 提到 上月、华南、产品 A，LLM 在回答里要提到这些上下文，让用户确认 LLM 理解了 query。

原则六：诊断显式。LLM 不仅回答数据，还要简要提到 SQL 的关键逻辑，让用户能验证。比如 我用 SUM(amount) 加 WHERE region='华南' 算的。

总结的失败处理。

失败一：数据为空。LLM 不能编一个数。必须告诉用户 当前数据中没有匹配记录，可能原因是 X。

失败二：数据异常。比如 SUM 返回 NULL（字段全空）。LLM 说 该字段在选定时间段内无数据，建议检查数据完整性。

失败三：SQL 执行失败。LLM 不参与回答，chayuan-desktop 直接展示错误。

失败四：结果验证失败。LLM 不参与回答，错误展示给用户。

总结的格式。chayuan-desktop 默认让 LLM 输出 简要回答 + 关键数据 + 可选解释。比如：

简要回答：上个月华南地区的销售总额是 1234567 元。

关键数据：12 笔订单，平均订单金额 102881 元，最大订单 500000 元。

可选解释：查询基于 2026-04-01 到 2026-04-30 的销售数据，按地区='华南' 过滤。

这种结构化的回答让用户既看到数字又看到上下文。

跨多源混合的总结。如果 query 同时调结构化和文档库，LLM 综合两边内容。chayuan-desktop 的 prompt 明确告诉 LLM 哪部分是 SQL 数据 哪部分是文档片段，让总结时分别引用。

LLM 的总结模型选择。chayuan-desktop 默认用主对话模型做总结。某些场景可以用专门的 总结模型（更小更便宜的模型），减少成本。配置开关让用户选。

中文总结的风格。LLM 默认用 中文办公风 总结，不要俏皮也不要过分严肃。chayuan-desktop 的 prompt 给一个 风格示例 让 LLM 跟着风。

引用气泡的展示。总结后的回答下面挂引用气泡（SQL + 表 + 行数）。用户能一边看自然语言一边核对原始数据。

国产化支持下的总结风格。中文办公场景的语言习惯（用 共 X 个 而不是 总共 X 个），chayuan-desktop 的 prompt 给国产模型（文心、通义）和海外模型（GPT-4o、Claude）分别提示，让风格统一。

WPS AI 插件 chayuan-wps 把 LLM 总结的回答直接显示在 WPS 边栏。用户可以一键 插入到 WPS 文档，把这段自然语言加上引用作为报告的一部分。这种工作流是数据分析转报告写作的核心。

LLM 自然语言总结让结构化查询的结果 易读、可用、可引用。免费开源的AI软件 把 SQL 数据 转 报告语言 这件事做得自然，是结构化 KB 真正可用的关键。
