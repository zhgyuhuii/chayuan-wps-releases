# 结构化结果的诊断信息 SQL 表 行 时间四件套

chayuan-desktop 桌面单机版的 text2sql 不只返回查询结果，还附带诊断信息。这一篇讲诊断信息的具体内容和用途。

先看诊断信息为什么必要。结构化查询不像文档 RAG 那样直观（点击引用看原文）。SQL 是个数学公式，结果的可信度需要其他信号。诊断信息让用户能验证 这个结果靠不靠谱。

诊断四件套。

第一件：SQL。生成的实际 SQL 语句。前端在引用气泡里展示（折叠显示）。用户可以看 LLM 怎么写的 SQL，判断逻辑是否正确。

第二件：表。SQL 涉及的表名列表。一个 SQL 可能涉及一张表（简单查询）或多张表（JOIN）。前端列出所有表，让用户知道数据从哪里来。

第三件：行数。返回行数。用户能看到 这次查询命中了 12 行 这种信息。这是 检索精度 的直接信号。如果你期望几百行结果但只返回 3 行，可能 WHERE 条件太严。

第四件：时间。SQL 执行耗时。慢 SQL 是性能信号。如果一个简单查询花了 5 秒，可能数据库索引没建对，或者数据太多。

四件套之外的可选信息。

第五件：执行计划。某些数据库支持 EXPLAIN。chayuan-desktop 可选展示执行计划，对开发者排查性能问题有用。

第六件：影响行数。INSERT/UPDATE/DELETE 的影响行数。但 chayuan-desktop 默认禁止写操作，这个字段一般不出现。

第七件：数据库会话信息。会话 ID、连接 ID。开发者排查问题用。

诊断信息的展示。前端引用气泡折叠态显示一行 SQL 摘要 + 行数 + 耗时。展开态显示完整 SQL（语法高亮）+ 表列表 + 数据预览（前 10 行）。再展开看完整数据（最多 100 行）。

数据预览的安全。诊断信息可能泄露敏感数据（如果用户白名单没设好）。chayuan-desktop 默认遵循白名单，但提醒用户在导出诊断报告时确认是否含敏感信息。

诊断信息的导出。chayuan-desktop 支持把诊断信息导出成 CSV 或 Excel。某些用户希望把 AI 算的数据 直接拿到 Excel 里二次加工，这个功能直接支持。

调试用法。开发者用诊断信息排查 text2sql 失败。

场景一：SQL 写错。诊断里看 SQL，发现 LLM 生成的 SQL 缺 GROUP BY 子句。回去调整字段注释或者补一个示例。

场景二：行数不对。诊断里看行数 0，发现 WHERE 条件 created_at >= '2026-01-01' 在数据集上没数据。原来用户的数据库里最新数据只到 2025。

场景三：耗时长。诊断里看 30 秒接近超时。原来 SQL 在大表上做了全表扫描。建议数据库管理员加索引。

诊断信息的存储。每次 text2sql 跑出来的诊断写到 audit_log 表。某些场景需要审计回放，能查到 这次 query 跑了什么 SQL 命中多少行 这种历史。

LLM 错误的捕获。LLM 偶尔生成不合法 SQL（语法错）。诊断里展示 SQL 解析失败原因，方便排查。

跨数据库的诊断。不同数据库返回的诊断字段名略有差异（PG 的 query_planner_runtime vs MySQL 的 query_time）。chayuan-desktop 在诊断展示时归一化字段名。

国产化支持下的诊断。达梦、金仓的 EXPLAIN 输出格式跟 PG 类似但有微差。chayuan-desktop 的诊断模块对国产数据库输出做了格式适配。

诊断信息的隐私。某些场景下用户希望关掉诊断（怕暴露 SQL 给同事看）。chayuan-desktop 支持 简化模式 只展示行数和时间，不展示 SQL。

WPS AI 插件 chayuan-wps 在 WPS 里展示诊断时简化为一行（SQL 摘要 + 行数）。点击展开能看完整 SQL。这种 简化默认 + 详情展开 的模式让 WPS 里的体验干净。

四件套诊断信息让结构化查询的结果 看得见、可验证。免费开源的AI软件 跟黑盒 SaaS 服务的差别就在这种 透明度。chayuan-desktop 在结构化 KB 上的诊断设计是这种态度的具体落地。
