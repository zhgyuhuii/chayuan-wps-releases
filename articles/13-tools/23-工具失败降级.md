# 工具的失败降级 多次失败后的兜底

chayuan-desktop 桌面单机版的工具失败有降级链。多次失败后兜底。这一篇讲。

## 降级的层次

层一：自动重试。某次失败立即重试 1-2 次。

层二：fallback 工具。某工具持续失败，切换备份工具。

层三：人工介入。工具完全不可用时让用户手动操作。

## 自动重试

某次工具调用失败。chayuan-desktop。

第一。判断错误类型。

429 限速 → 等 Retry-After 后重试。

5xx 服务器错误 → 立即重试 1 次。

网络错误 → 立即重试 1 次。

业务错误（404、400）→ 不重试（重试无意义）。

第二。重试一次仍失败 → 进入 fallback。

## fallback 工具

某些工具有功能等价的备份。

```yaml
fallbacks:
  github_mcp.list_repos:
    - github_mcp_alt.list_repos  # 第二个 GitHub mcp 实例
    - manual_search  # 让用户手动搜
```

第一个工具失败时调第二个。

## 用户级别 fallback

LLM 看到工具失败时能尝试用其他工具实现同样目的。

```
LLM 调 send_email 失败。
LLM 思考：能不能用 dingtalk_mcp.send_message 替代？
LLM 调 dingtalk_mcp.send_message 成功。
```

LLM 自主降级。chayuan-desktop 给 LLM 看到所有可用工具，LLM 自己组合。

## 手动介入

某些场景所有自动方法都不行。chayuan-desktop 弹提示。

```
工具调用失败：
  send_email 失败 3 次
  dingtalk_mcp 不可用
  
请手动发送邮件给 legal@corp.com，主题是 "..."
```

让用户接管。

## fallback 链的配置

用户能配置 fallback 链。

```yaml
intent_fallbacks:
  send_message:
    - send_email
    - dingtalk_mcp.send
    - wechat_work.send
    - sms_mcp.send
  search_info:
    - kb_search
    - web_search
    - manual
```

某意图按链路尝试。

## fallback 的可观测

监控面板。

```
最近 7 天 fallback 触发：
  send_email → dingtalk_mcp: 12 次
  github_mcp → manual: 3 次
```

让用户看到主工具频繁失败时切到了哪。

## 主工具的恢复

chayuan-desktop 后台定期检测主工具是否恢复。

```
每 5 分钟探测 send_email（轻量调用）。
连续 3 次成功 → 标主工具恢复，下次优先用。
```

不让 fallback 永久取代主工具。

## 用户的容错偏好

某些用户希望 工具失败立即告诉我，不要 fallback。

某些用户希望 工具失败 LLM 自己想办法解决，不打扰我。

chayuan-desktop 设置里能选。

## 国产化场景

党政军场景某些工具偶发故障（网络抖动、配额耗尽）。chayuan-desktop 的 fallback 让用户体验稳定。

某些场景对工具调用有严格审计。失败和 fallback 都要审计记录。chayuan-desktop 的审计满足。

## chayuan-server 的对应

chayuan-server 多用户场景下 fallback 是企业级（管理员配置）。chayuan-desktop 单机用户级。

## WPS 加载项

chayuan-wps 在 WPS 里调用工具失败时同样走 fallback。员工感知就是 工具一般能成功，偶尔某次自动换了一个。

## 总结

工具的失败降级是 chayuan-desktop 在工程鲁棒性上的设计。免费开源的AI软件 让 工具失败 不让用户陷入等待。chayuan-desktop 的自动重试 + fallback 工具 + LLM 自主降级 + 人工介入四层让工具调用在工程上稳。
