# 工具的并发与序列化 模型并行调用的处理

chayuan-desktop 桌面单机版的工具并发由模型决定。这一篇讲并行调用的处理。

## 模型的并行调用

OpenAI 和 Anthropic 都支持 parallel_tool_calls。一轮 LLM 决定调多个工具，并行执行。

例：用户问 GitHub 上我有几个 repo，Slack 上的待办几个。

LLM 一轮决策：

```json
{"tool_calls": [
  {"name": "github_mcp.list_repos"},
  {"name": "slack_mcp.list_todos"}
]}
```

两个工具能同时跑。

## chayuan-desktop 的并发实现

chayuan-desktop 收到多个 tool_calls。

启动每个工具调用为独立任务。

asyncio 并发执行。

等所有任务完成后整合结果。

返回给 LLM。

```python
async def execute_tools(tool_calls):
    tasks = [execute_single(tc) for tc in tool_calls]
    results = await asyncio.gather(*tasks)
    return results
```

简单干净。

## 并行的好处

延迟降低。两个 1 秒的工具调用并行后总耗时 1 秒，而非 2 秒。

用户体验流畅。

## 并行的副作用

某些工具不能并发（前面文章讲过的本地 LLM）。chayuan-desktop 的工具调度知道这点。

```
github_mcp 多实例 → 并发 OK
slack_mcp 单实例 → 队列处理
ollama 本地 LLM → 单实例排队
```

## 失败的处理

并行 3 个工具，其中 1 个失败。

策略一：等所有完成。失败的返回错误，成功的返回结果。LLM 看到决定怎么处理。

策略二：fail-fast。一个失败立刻取消其他。某些场景适用（比如所有工具都依赖同一前置）。

chayuan-desktop 默认策略一。LLM 自己决定容错策略。

## 顺序依赖

某些场景工具调用有顺序依赖。

第一步：search_kb 拿数据。

第二步：基于数据调 send_email。

LLM 不会并行这两个（语义上不可并行）。会分两轮。

第一轮：tool_calls=[search_kb]。

第二轮：tool_calls=[send_email]。

每轮内可以并行多个无依赖工具。

## 用户感知

UI 显示并行调用。

```
[同时进行]
  ⏳ github_mcp.list_repos
  ⏳ slack_mcp.list_todos
[完成]
  ✓ github_mcp.list_repos (234ms)
  ✓ slack_mcp.list_todos (456ms)
```

用户看到并行执行的视觉效果。

## 资源限制

并发数过高耗资源。chayuan-desktop 限制每会话最多 5 个工具同时跑。超过的排队。

```yaml
tools:
  max_parallel_per_session: 5
  max_parallel_global: 20
```

## 工具间的资源竞争

并发工具可能竞争 GPU、网络等。chayuan-desktop 的资源调度协调。

```
ollama 推理（GPU）
embedding（GPU）
某些 mcp 工具（CPU）
```

GPU 任务串行，CPU 任务并行。chayuan-desktop 智能调度。

## 国产化场景

党政军场景对工具并发不敏感（用户量少）。chayuan-desktop 默认即可。

## chayuan-server 的对应

chayuan-server 多用户场景下并发管理更复杂（全局共享资源）。chayuan-desktop 单机简化。

## WPS 加载项

chayuan-wps 在 WPS 里调用多工具时跟桌面端共享并发资源。统一调度。

## 总结

工具的并发与序列化是 chayuan-desktop 在工具调用性能上的工程优化。免费开源的AI软件 让 并行调用 提升效率。chayuan-desktop 的 asyncio 并发 + 资源调度 + 限流让 多工具协作 在工程上稳。
