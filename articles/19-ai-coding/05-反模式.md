# Claude协作的反模式 哪些事不要交给它

chayuan-desktop 桌面单机版用 Claude 协作多年的经验，也总结出一些 不该交给 Claude 的事。这一篇讲反模式。

反模式一：让 Claude 做架构决策。

错法。让 Claude 选 sqlite-vec 还是 Milvus 默认。让 Claude 决定 Tauri 还是 Electron。

为什么不行。架构决策涉及产品定位、长期维护、团队能力。Claude 给建议但不能替人判断。chayuan-desktop 的所有大架构决策（前面文章讲过）都是人主导。

正确做法。让 Claude 给候选方案的优劣对比，人决定。

反模式二：让 Claude 写凭据相关代码。

错法。让 Claude 实现密钥管理。让 Claude 写 OAuth 流程。

为什么不行。凭据涉及密码学正确性，Claude 偶尔出错。一行错的代码可能让所有用户的密钥泄露。

正确做法。凭据相关用经过审计的库（Stronghold 等）。Claude 协助调用这些库，但不让 Claude 自己写加密算法。

反模式三：让 Claude 做合规审视。

错法。让 Claude 决定 这个数据要不要 PII 脱敏。

为什么不行。合规涉及法律，需要懂当地法律的人判断。Claude 知识可能过时。

正确做法。合规规则人定，Claude 实现。

反模式四：让 Claude 决定何时发布。

错法。让 Claude 看 PR 列表说 现在可以发版了吗。

为什么不行。发版涉及业务节奏、市场时机、客户合同。Claude 不懂这些。

正确做法。版本节奏人决定。

反模式五：让 Claude 跟客户对话。

错法。把客户问题交给 Claude 直接回答。

为什么不行。客户对接涉及人际、商务、长期关系。Claude 不能替代客户成功。

正确做法。Claude 帮整理问题答复草稿，人审视后回答。

反模式六：让 Claude 删代码不审视。

错法。Claude 说 这段代码看起来没用，删了。开发者直接合并。

为什么不行。Claude 不知道某段代码可能在某个特殊场景被用。或者维护历史。

正确做法。Claude 标记 看起来未用，人确认是否真的未用。

反模式七：让 Claude 改 git history。

错法。让 Claude force push、改提交历史。

为什么不行。git history 是工程记录。改了之后协作者的本地仓库混乱。

正确做法。新代码新提交。需要修复历史走 revert + 新提交。

反模式八：让 Claude 自动化所有 PR 操作。

错法。Claude 自己写代码自己合并。

为什么不行。PR 必须有人 review。即使 Claude 写的代码也要人审。

正确做法。Claude 写 PR 草稿，人 review 合并。

反模式九：让 Claude 跑生产部署。

错法。让 Claude 直接 deploy 到生产环境。

为什么不行。生产部署涉及业务影响。出问题 Claude 不能负责。

正确做法。部署人工触发。Claude 协助生成部署脚本。

反模式十：依赖 Claude 不复盘。

错法。代码 Claude 写的，用着用着出 bug，找 Claude 修。

为什么不行。Claude 不一定能修自己的 bug。开发者要懂代码，复盘 bug 跟修复。

正确做法。Claude 协助开发，但开发者保持对代码的深入理解。

WPS AI 插件 chayuan-wps 的协作同样适用这些反模式。

Claude 协作的反模式是 chayuan-desktop 团队的踩坑教训。免费开源的AI软件 用 AI 工具是为了提效不是为了替代判断。chayuan-desktop 在这一面的纪律让 AI 协作 不偏离工程主线。
