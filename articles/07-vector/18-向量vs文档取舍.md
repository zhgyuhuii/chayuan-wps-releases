# 向量库与文档RAG的取舍 什么时候不要用向量

chayuan-desktop 桌面单机版默认走向量召回 + 重排做 RAG。但向量不是万能。某些场景用别的方法更好。这一篇讲什么时候不要用向量。

先看向量 RAG 适合什么。

适合一：开放式问答。问 关于压力测试的内容，向量召回能找到含 压力测试 语义相关的 chunk。

适合二：跨语种检索。query 跟 chunk 不同语言但语义相近，向量能召回。

适合三：模糊匹配。query 用了同义词，向量能识别。

不适合的场景。

不适合一：精确匹配。问 订单号 12345 的状态。向量召回不擅长精确字符串匹配。这种场景该走全文检索（BM25）或者 SQL 直接查。

不适合二：聚合查询。前面文章讲过。问 多少、几个、总和，必须走 SQL。

不适合三：实时数据。向量库索引是预先建好的，新数据要等下次更新。如果用户问 最新 10 条订单，应该 SQL 直接查实时数据，不走向量。

不适合四：精确值过滤。问 金额超过 100 万的合同。这种 数值比较 应该 SQL 而不是向量。

不适合五：复杂关系。问 用户 A 跟用户 B 的共同关注点。这种 跨表跨实体关系 SQL 强于向量。

向量 + 其他方法的混合。

混合一：向量 + BM25（hybrid search）。ES 8 原生支持。chayuan-desktop 接 ES 时可开 hybrid 模式。某些 query 既需要语义又需要关键词。

混合二：向量召回 + LLM 推理。向量给候选 chunk，LLM 跨 chunk 推理。这种是经典 RAG 模式。

混合三：SQL 加 向量（混合 KB）。同一份数据建两种 KB，按 query 类型分别走。

混合四：先 SQL 过滤再向量召回。比如先 SQL 过滤 部门=技术部 + 时间=2026Q1 拿到 chunk_id 列表，再在这些 chunk 里向量检索。这种 metadata 过滤 + 向量 在 chayuan-desktop 上原生支持。

什么时候考虑切换 RAG 模式。

信号一：召回不准。同样 query 反复测试都召不回相关 chunk。可能 chunk 切分不当，或者 query 跟内容语义跨度大，重新设计 chunk 或者换 embedding 模型。

信号二：结果完全不相关。向量召回返回了高 score 但内容跟 query 完全不相干。可能向量空间训练偏差，换重排或者换 embedding 模型。

信号三：精确查询失效。query 含具体 ID 或具体值但向量召不回。改用 SQL 或全文检索。

信号四：聚合需求多。用户经常问 多少 几个 总数，应该建结构化 KB。

reverse 思考。某些场景大家以为该用向量，其实不该。

例子一：查找特定文档。问 张三 2025 年签的合同。向量可能召不回（命中里没 张三 2025），SQL 直接查 author='张三' AND signed_year=2025 更准。

例子二：查找最新内容。向量索引滞后，新内容可能没建索引。SQL 加 ORDER BY created_at DESC LIMIT 10 直接拿最新。

例子三：枚举所有。问 所有部门有哪些。SQL 直接 SELECT DISTINCT department，向量没法穷举。

例子四：精确字段。问 phone 13800001234 的客户。SQL 直接查，向量召不回（数字字符串不是语义检索的强项）。

chayuan-desktop 的智能选择。router 模块识别 query 意图，自动选向量召回还是 SQL 还是其他。前面 router 文章详细讲过。用户基本不用懂何时该用向量。但开发者建 KB 时要懂。

国产化支持下的取舍。中文场景下向量召回 + 重排精度好。但精确查询、聚合、枚举仍走 SQL。chayuan-desktop 的多类型 KB 让这种 按需选用 自然成立。

WPS AI 插件 chayuan-wps 透明用 router 决策。在 WPS 里发问时不用懂背后是向量还是 SQL。

向量库与文档 RAG 的取舍是 chayuan-desktop 多源能力的核心判断。免费开源的AI软件 不应该把所有问题都丢给向量。chayuan-desktop 的多类型 KB + router 智能让 用对工具 自然发生。
