# 加载项与桌面端的版本对账 v3.0 之后的兼容期

chayuan-wps 加载项跟 chayuan-desktop 后端的版本兼容是工程关键。这一篇讲。

## 版本演化的挑战

chayuan-wps 加载项独立发布。

chayuan-desktop 桌面后端独立发布。

两者升级节奏不一致。

可能场景。

加载项 v3.0，后端 v3.0：兼容。

加载项 v3.1，后端 v3.0：加载项用了新接口后端不支持。

加载项 v3.0，后端 v3.1：后端有新功能加载项不用。

## v3.0 的合同

v3.0 是关键节点。统一 ku_ids 合同。

加载项 v3.0+ 用 ku_ids 字段（前面文章讲）。

后端 v3.0+ 接受 ku_ids。

加载项 v2.x 用旧字段（kb_names）。后端 v3.0+ 兼容旧字段。

## 兼容期

v3.0 发布后给 6 个月兼容期。

旧加载项（v2.x）能用新后端（v3.x）。

旧后端（v2.x）能用新加载项（v3.x）。但加载项的某些新功能用不了。

期满后停止 v2.x 支持。强制升级到 v3.x。

## 版本协商

加载项启动时探测后端版本。

```
GET http://127.0.0.1:62581/api/v1/version
返回: {"version": "3.1.0", "compatibility": ["v3.x", "v2.x_legacy"]}
```

加载项根据后端版本启用 / 禁用某些功能。

```
if (backend.version >= "3.1") {
    // 启用工具调用功能
} else {
    // 不显示工具调用按钮
}
```

## 用户提示

加载项检测到版本不匹配。

```
您的 chayuan-desktop 后端 v2.5.0
chayuan-wps 加载项 v3.0.0
建议升级 chayuan-desktop 到 v3.0+ 以使用全部功能。
[升级] [继续使用兼容模式]
```

## 跨版本 API 设计原则

后端 API 演进遵循。

向后兼容。新版本不删旧字段。

新字段可选。旧客户端不传新字段也能工作。

错误格式稳定。错误码不变。

弃用渐进。某字段先标 deprecated 警告几个版本，再真正移除。

## 加载项的回退

加载项检测后端不支持某功能。

不显示按钮。

或调用时降级。

```js
async function chat() {
  if (capabilities.includes("tools")) {
    return chatWithTools();
  } else {
    return basicChat();  // 降级
  }
}
```

## 协议契约的测试

CI/CD 跑跨版本兼容性测试。

加载项 v3.x × 后端 v3.x 各组合都测。

防止某次升级破坏跨版本兼容。

## 实战场景

某政企 chayuan-desktop 装的是 v3.0。chayuan-wps 加载项更新了 v3.2。

员工启动 WPS。chayuan-wps 检测后端 v3.0。

```
某些新功能（视觉对话）需要后端 v3.1+。当前可用功能略少。
```

员工继续用基本功能。等 IT 升级 chayuan-desktop 到 v3.1+。

## 国产化场景

党政军内网升级慢（审批流程长）。chayuan-wps 跟 chayuan-desktop 版本差异常见。版本兼容期是必要工程基础。

## chayuan-server 的对应

chayuan-server 模式下版本管理类似。chayuan-wps 跟 chayuan-server 也有版本对账。

## 总结

加载项与桌面端的版本对账是 chayuan-desktop + chayuan-wps 长期演进的工程关键。免费开源的AI软件 让 升级不破坏旧客户端。chayuan-desktop 的版本协商 + 兼容期 + 渐进弃用让两个独立组件能各自演进又协同工作。
