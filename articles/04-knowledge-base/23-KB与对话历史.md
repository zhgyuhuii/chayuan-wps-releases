# KB与对话历史的关系 引用是否也跟着导

chayuan-desktop 桌面单机版的 KB 跟对话历史是两个相对独立的数据集合。但它们之间通过 ku_id 引用形成关联。这一篇讲清楚 KB 跟对话的关系，以及导出导入时引用的处理。

先看两者的存储。KB 数据在 CHAYUAN_ROOT/data/chayuan.db 的 kb 表 + chunk 表 + KB 各自的 vectors/*.db 文件。对话历史在 CHAYUAN_ROOT/data/chayuan.db 的 conversations 表 + messages 表。两者都在同一个 SQLite 文件里，通过 ku_id 字符串关联（messages 的 metadata 里有引用列表）。

对话历史里的引用结构。每条 assistant 消息的 metadata 里有 citations 字段，是一个数组。每个 citation 含 chunk_id、ku_id、score、preview、original_position。点击引用气泡时前端按 chunk_id 去查 KB 内容。

KB 删除对历史的影响。如果某个 KB 被删除，历史会话里引用它的气泡变成 灰色，文字仍可见但点击展开提示 该 KB 已删除。这种 graceful 处理让历史不至于完全损坏。

导出对话不带 KB 怎样。chayuan-desktop 支持单独导出对话历史（不导出 KB）。导出的 zip 包里只有 conversations 和 messages 表。在新机器 import 后历史能看到，但引用点击展开提示 该 KB 在当前系统不存在。

导出对话带 KB 怎样。chayuan-desktop 也支持把对话和相关 KB 一起导出。这种打包方式让新机器 import 后历史的引用能正常展开。但导出 zip 体积大（含 KB 数据），传输成本高。

只导 KB 不导对话。最常见。chayuan-desktop 的 export 工具默认只导 KB，对话历史是另一个开关。这种分离让 我换电脑只想要资料 这种场景方便。

对话历史是否敏感。某些用户的对话历史里可能含敏感信息（公司内部讨论、私人问题）。chayuan-desktop 的 export 工具默认不导对话历史，避免无意泄漏。用户主动选择导出时再带上。

历史会话的搜索。chayuan-desktop 支持在对话历史里全文搜索。比如搜 关于产品 A 的对话，能找到所有提到产品 A 的对话。历史搜索不依赖 KB，是独立的对话内容索引。

对话历史的 KB。chayuan-desktop 路线图里有一个想法：把对话历史作为一种特殊 KB（命名空间 history:*），让用户能从 AI 那里问 我之前问过类似问题吗 这种问题。当前还没实现，未来加。

KB 数据更新对历史的影响。如果一个 KB 的某个 chunk 被改了（用户更新了原文件），历史会话里引用旧 chunk 的气泡可能展示成更新后的内容。这是 chayuan-desktop 的 lazy 解析：每次点击引用时实时去 KB 查 chunk，不缓存历史快照。这种行为对 实时性 友好，但对 历史一致性 友好度低。

如果需要历史快照。chayuan-desktop 当前不冻结引用快照。某些合规场景需要 历史回答永远显示当时的引用文本，这个需求要靠 export + 不再修改 KB 的纪律来实现，或者升级到企业版的快照机制。

跨用户分享对话怎样。单机版下没有用户概念，对话不能分享。如果你想把一段对话给同事看，导出对话 zip + 把 zip 给他 + 他 import 到自己 chayuan-desktop。引用的 KB 如果不在他机器上就显示 灰色。

对话历史的 token 计费记录。chayuan-desktop 把每次对话调用的 token 数记到 usage 表。这个数据可以导出做统计。对话历史导出时同步导出 usage 数据。

国产化支持下的对话审计。政企场景需要保留对话审计日志。chayuan-desktop 的 audit_log 表记录每次 KB 访问、模型调用、工具调用，跟对话历史关联。这些日志按合规要求长期保留。

WPS AI 插件 chayuan-wps 共用同一份对话历史。在 WPS 里发起的对话进入桌面客户端的历史列表。WPS 加载项里也能看到桌面发起的对话。这种统一让用户感觉 chayuan-desktop 加 chayuan-wps 是一个产品。

KB 跟对话历史的关系是 chayuan-desktop 数据架构的一对核心关联。免费开源的AI软件 把这两个东西的边界做清楚，导出导入备份才有清晰的语义。
