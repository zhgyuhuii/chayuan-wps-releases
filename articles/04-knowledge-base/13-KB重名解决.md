# KB名称冲突怎么解决 命名空间隔离的内部约定

chayuan-desktop 桌面单机版让用户自定义 KB 名。问题来了：用户起名字时不知道有没有跟现有 KB 冲突，重名怎么办。这一篇讲清楚 chayuan-desktop 的命名空间隔离和重名处理。

先看命名空间。chayuan-desktop 的 KB 按命名空间隔离：doc:* 是文档库、src:* 是外部源、office:* 是办公私库。同一命名空间内 KB 名不能重复，跨命名空间不冲突（doc:技术资料 和 office:技术资料 可共存）。

doc:* 的命名规则。冒号后面是用户自定义名字，比如 doc:技术资料。chayuan-desktop 强制 doc:* 内 KB 名唯一，新建时如果重名会拒绝并提示。用户必须改名才能创建。

src:* 的命名规则。冒号后面是连接器实例 ID，由 chayuan-desktop 自动分配（src:milvus_local_xyz 这种带后缀的 ID）。用户看到的 显示名 是另一个字段，可以重复。这种设计让用户不用关心 ID 唯一性。

office:* 的命名规则。冒号后面是 owner 名 + 可选 group 名。office:zhangsan 跟 office:zhangsan:team_a 是两个不同的 KB，互不冲突。同一个 owner 下不能有两个 default group。

新建 doc:* 时的重名处理。用户输入名字 技术资料，chayuan-desktop 检查是否已经有 doc:技术资料。如果有，前端立刻提示 已存在，建议改名。用户可以选 改名 或者 替换（替换需要二次确认）。

软删除 KB 的名字回收。如果 doc:技术资料 被软删除（在回收站里），新建一个同名 KB 怎么处理。chayuan-desktop 默认拒绝创建（因为 30 天内可能要恢复）。用户可以选 在回收站里彻底删除旧 KB 之后再创建新的，或者新 KB 用不同名字。

跨命名空间的同名共存。doc:报告 和 office:zhangsan:报告 是两个 KB。前端展示时按命名空间分组，用户能区分。检索时用户勾哪个 KB 对应哪个 ku_id。

KB 名字的字符约束。chayuan-desktop 允许中文、英文、数字、空格、连字符、下划线。不允许冒号（: 是命名空间分隔符）、斜杠（/ \ 是路径符）、引号（' "）、控制字符。超过 50 字符自动截断。

显示名跟内部 ID 的差异。chayuan-desktop 内部用 kb_id（UUID 或自增 ID）作为 KB 的真主键，KB 名只是 显示名 + 用户输入的便利。即使 KB 名重命名也不影响 kb_id。引用气泡里的 ku_id 是 doc:KB名 形态，但内部解析时按 kb_id 跟踪。

KB 重命名。chayuan-desktop 允许给已有 KB 改名。改名后 ku_id 也跟着变（因为 ku_id 含 KB 名）。但是历史会话里引用的 ku_id 仍是旧名，chayuan-desktop 会做映射兼容（kb_id 不变）。

跨电脑迁移的命名一致。chayuan-desktop 单机版没有云端，每台电脑独立命名。用户在工作笔记本和家用台式上都建了 doc:技术资料，但内部 kb_id 不同，是两个 KB。如果想真同步，要走 export/import 工具。

国产化支持下的命名约束。中文 KB 名在政企场景下常见。chayuan-desktop 全 utf-8 处理，没有兼容问题。但建议 KB 名简短（不超过 20 字符），便于 UI 展示。

WPS AI 插件 chayuan-wps 共用同一份 KB 列表，命名规则一致。在 WPS 加载项里挑 KB 时按 ku_id 选择，不会因为重名出问题。

冲突的几种边界场景。一是大小写敏感。chayuan-desktop 的 KB 名大小写敏感，doc:Report 和 doc:report 是不同 KB。建议用户统一用一种大小写风格。二是空格处理。前后空格自动 trim，中间空格保留。三是 Unicode 标准化。某些 unicode 字符有多种写法（NFC vs NFD），chayuan-desktop 在保存前统一到 NFC，避免 看起来一样实际不同 的 KB 名。

未来的命名空间扩展。如果加新命名空间（mem:* agent memory，stream:* 流式数据），命名规则跟现有保持一致。新命名空间的 KB 名跟 doc:* 不冲突。

命名空间隔离这件事看起来工程细节，但对用户体验影响实在。chayuan-desktop 的命名规则让 同事的 office 库 跟 我的 doc 库 即使同名也不混淆。免费开源的AI软件 想让普通用户不用懂命名细节就能用，命名空间是最稳的保护。
