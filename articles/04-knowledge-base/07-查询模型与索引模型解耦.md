# 全模型支持下的查询模型与索引模型解耦 不能在查询时换

chayuan-desktop 桌面单机版的本地离线知识库 有一个工程上的硬约束：查询时用的嵌入模型必须跟建库时用的嵌入模型一致。这个看起来普通的规则在工程上常被忽视。这一篇讲清楚为什么不能查询时随便换模型。

先看为什么这是个约束。每种嵌入模型生成的向量在不同维度的语义空间里。bge-m3 的向量空间跟 bce-embedding 的向量空间不同维度（都 1024，但语义编码不同），跟 GTE 的 768 维更不同。如果建库时用 bge-m3，查询时用 bce-embedding，query 向量在 bge-m3 空间里跟库内向量根本不在同一个 frame，距离计算无意义，结果纯属随机。

CLAUDE.md 里的明确要求。查询阶段不能让前端覆盖 embedding 模型；查询模型必须跟随知识库索引配置。这条规则不是约束开发者的灵活性，是约束代码不能允许 错误的灵活性。

正确的做法。每个 KB 在创建时记录使用的嵌入模型名（embedding_model_name 字段）。检索时先查 KB 的 metadata，拿到这个字段，用对应模型给 query 嵌入。这样 query 和库内向量在同一空间。

错的做法。有些设计允许前端在查询时选 嵌入模型，比如让用户挑 这次用 bge-m3 还是 bce-embedding。chayuan-desktop 拒绝这种设计。前端只能选 KB，不能在查询时选嵌入模型。模型已经被 KB 决定。

切换嵌入模型的正确流程。如果用户想换嵌入模型（比如从 bge-m3 换 bce-embedding），必须做完整的 重建索引：删除现有索引、用新模型重新嵌入所有 chunk、重建 sqlite-vec 索引。chayuan-desktop 提供这个 重建 操作，但需要明确告诉用户耗时（可能几分钟到几十分钟）和影响。

为什么不在 KB 上同时索引多种嵌入。理论上可以同一份 chunk 用多种嵌入分别生成向量索引。但是存储翻倍、维护翻倍，对单机版不划算。chayuan-desktop 一个 KB 只用一种嵌入。

混选 KB 时的嵌入处理。一次问答勾了多个 KB，每个 KB 可能用不同嵌入模型。chayuan-desktop 在嵌入计算阶段为每个 KB 用对应模型生成 query 向量。同一个 query 可能算两次嵌入（一次 bge-m3 一次 bce-embedding），给不同 KB 用。这个开销在毫秒级，不显著。

跨 KB score 比较的影响。不同嵌入模型的距离尺度不一样。chayuan-desktop 在多 KB 并联时做 score 归一化（每个 KB 内归一到 0-1），跨 KB 比较才有意义。

外部向量库的同样规则。Milvus、Chroma 等外部源的 collection 也有自己的嵌入模型记录。chayuan-desktop 在创建外部连接时记录 embedding_model_name 字段，查询时按这个字段给 query 嵌入。外部向量库的 collection 用什么模型由用户在外部建库时决定。

模型生效优先级。CLAUDE.md 里强调 用户选择 大于 默认 大于 自动。但这条规则只适用于对话模型选择，不适用于嵌入模型。嵌入模型不能被用户在查询时覆盖。

实际场景的混乱。早期某个版本允许前端发查询时带嵌入模型字段，后来证明这是坑：用户从一个聊天客户端搬过来 期望 prompt，结果回答全错。chayuan-desktop 直接禁掉了这个口子。

如果将来要支持嵌入模型升级。比如智源发布 bge-m3 新版本（精度更好），用户想升级。chayuan-desktop 的做法是支持 KB 重建索引：保留 KB 元数据和 chunk 文本，用新嵌入重新生成向量。这种升级是显式操作，不是查询时切换。

查询模型的不可覆盖在 API 设计上的体现。SearchRequest 没有 embedding_model 字段。如果你看到代码里有这个字段，那是 bug。

WPS AI 插件 chayuan-wps 共用同一份 KB 元数据。在 WPS 里查询时 sidecar 自动按 KB 元数据用对应嵌入模型，加载项侧不需要懂这件事。

不能查询时换模型 这条规则看起来是限制，实际上是保护。免费开源的AI软件 想保证检索结果的正确性，必须在工程层面把这种 错误用法 直接堵住。chayuan-desktop 的实现是这条原则的具体落地。
