# 跨KB引用的回链规则 多源混合时如何标注来源

chayuan-desktop 桌面单机版的回答里经常出现 跨 KB 引用：一段答案里既引用了文档库的内容又引用了结构化库的数据。这一篇讲多源混合时引用的回链规则，让用户能看清楚 这段话来自哪。

先看跨 KB 引用的典型场景。问 我们去年的销售数据怎么样，结合最新的市场分析报告。chayuan-desktop 的 router 识别出多源意图，同时跑 src:dm_finance（结构化销售数据）和 doc:市场分析（文档库）。LLM 拿到两边的命中后综合写答案。

LLM 怎么知道哪段话引用哪边。在 prompt 里 chayuan-desktop 给每个命中加唯一 chunk_id 标记：[chunk_42] 来自 src:dm_finance 的数据片段、[chunk_57] 来自 doc:市场分析 的文档片段。LLM 被指示在每段事实后用 [chunk_xx] 标注来源。

LLM 实际执行的合规度。不同模型差异大。GPT-4o 大致能精准标注，DeepSeek、文心、通义在指令清晰时也能配合。某些早期模型几乎不标注。chayuan-desktop 的 chat 模块对没标注的部分做兜底（基于内容相似度匹配回 chunk）。

引用气泡的展示。前端按 chunk_id 找回每个引用的 ku_id 和 metadata。doc:* 来源的引用渲染成蓝色气泡，src:* 来源的渲染成绿色气泡，office:* 渲染成橙色气泡。同一段答案后面可能挂多个气泡（混合来源）。

折叠组。chayuan-desktop 的引用展示在答案下方按 KB 分组。每组一个折叠面板：从 doc:市场分析 引用 5 段、从 src:dm_finance 引用 3 行、从 office:zhangsan 引用 1 段。这种分组让用户快速定位 哪个来源贡献了什么。

跨 KB 一致性的提示。LLM 综合两边的内容时偶尔会出现 矛盾结论：文档库里说 增长 10%，结构化库的实际数字是 12%。chayuan-desktop 不强制纠正这种矛盾，但在引用气泡里展示具体数字，让用户自己判断。

引用顺序。一段话的多个引用按 score 降序排列。score 高的（更相关的）排在前面。如果一段话里既有 SQL 命中（score 通常视为 100%）又有文档命中（score 80%），SQL 优先。

跨 KB 的去重。某些资料在多个 KB 里同时存在。比如年度报告既被入到 doc:年度报告，又被同事转贴到 office:zhangsan:summary。两边的 chunk 内容相似。chayuan-desktop 在 results 聚合时检测内容相似度（基于哈希或 BM25），相似度高的合并展示，引用气泡里显示 来自 2 个 KB。

跨 KB 引用的下载按钮。每个引用按自己 ku_id 的能力决定。doc:* 引用支持下载原文件、跳页。src:* SQL 来源不支持下载文件，但能展开 SQL。office:* 跟 doc:* 类似但带 owner 标识。前端按 kind 分流。

模型限速对跨 KB 的影响。多源混合时 LLM 要处理更多上下文，token 数增加，调用厂商时容易撞限速。chayuan-desktop 的限速排队机制照常工作，但用户体感延迟可能更长。

跨 KB 的权限问题。如果一次问答涉及的 KB 中有当前用户没权限的，chayuan-desktop 直接从 ku_ids 里过滤掉，不让 LLM 看到那个 KB 的内容。引用气泡里也不会出现该 KB。多用户版本下这条规则严格。

国产化支持下的跨 KB 场景。常见的 国产数据库 + 文档库 组合：达梦销售台账 + Word 销售报告。chayuan-desktop 的 router 能识别这种组合的意图，引用展示能区分 SQL 数据 vs 报告文字。

WPS AI 插件 chayuan-wps 的跨 KB 引用展示。在 WPS 边栏里按 KB 分组展示引用气泡。点击 doc 来源跳到对应 PDF 页或者 Word 段落。点击 SQL 来源展开 SQL 详情面板。

跨 KB 引用是 chayuan-desktop 多源 RAG 的体验高地。免费开源的AI软件 想让用户在多源场景下不迷失，引用回链的精细化是关键。chayuan-desktop 在这件事上做的工作让答案 可信 加 可追 同时成立。
