# 本地离线知识库的多KB并联检索 实测延迟与并发上限

chayuan-desktop 桌面单机版支持一次问答检索多个 KB。这种 多 KB 并联 是真实使用中常见的需求。这一篇讲多 KB 并联的实测延迟、并发上限、注意事项。

先看 多 KB 并联 是什么。用户在 KB 选择器里勾了 5 个 KB：3 个文档库 doc:技术资料 doc:合同档案 doc:市场分析、1 个结构化 src:dm_finance、1 个个人办公 office:zhangsan。一句话问出来，chayuan-desktop 同时在这 5 个 KB 上检索，结果聚合后让模型综合回答。

并发模型。orchestrator 用 asyncio.gather 把多个检索任务并发跑。文档库的 sqlite-vec 查询是 IO 密集（磁盘读），结构化的 SQL 查询是网络 IO（外部 PG/达梦），办公库的命名空间过滤是 sqlite 查询。这些任务大多是 IO，asyncio 并发让总耗时接近最慢那个，而不是所有相加。

实测延迟。在一台 i7 加 32G 加 SSD 的开发笔记本上：

5 个文档库（每个 5-10 万 chunk）并联检索，整体延迟 200-400ms。
3 个文档库 + 2 个外部 SQL（达梦 + PG）并联，延迟 500-800ms（外部 SQL 网络延迟拖慢）。
3 个文档库 + 1 个外部 Milvus（百万级 collection）并联，延迟 300-600ms。
5 个外部 SQL 库并联，延迟 800ms 到 2 秒（取决于网络和 SQL 复杂度）。

这些延迟在 LLM 调用本身（2-5 秒）之前完成，对最终响应影响不大。

并发上限。chayuan-desktop 默认设置每次问答最多 10 个 KB 并联。超过的会按 score 截断。这个上限是为了避免大量 KB 让 LLM 上下文爆炸。用户实际场景大多 1-5 个 KB，10 个上限够用。

LLM 上下文限制。每个 KB 的检索命中要喂给 LLM 作为上下文。LLM 的上下文窗口有限（gpt-4o 128k、claude-3-opus 200k、长文模型可能 1M）。chayuan-desktop 在多 KB 并联时按预算分配每个 KB 的 chunk 数量，避免上下文溢出。比如 5 个 KB 共享 100 个 chunk 名额，每个 KB 平均 20 个；如果某个 KB 命中精度高，可以多分。

并联失败的隔离。某个 KB 检索失败（外部源不可达、SQL 错误、向量库连接断开）不应该让整个查询失败。chayuan-desktop 的 orchestrator 对每个任务做错误隔离，失败的 KB 在结果里标记 unavailable，其他 KB 正常返回。前端展示时给用户提示 部分 KB 检索失败。

并联结果聚合。每个 KB 返回一组 RetrievalHit。results 模块按 score 排序，但跨 KB 的 score 不一定可比（不同 adapter 的 score 计算方式不同）。chayuan-desktop 做归一化：每个 KB 的 score 先在自己的命中里归一到 0-1 区间，再加权聚合。文档库的 score 含重排，结构化的 score 含 SQL 执行成功标志，向量库的 score 是原始距离。

去重。多个 KB 可能命中同一份资料的不同版本。chayuan-desktop 检查 metadata 里的文件路径或 chunk 内容相似度，做去重。这个步骤避免 LLM 看到重复信息。

排序权重。用户可以在前端给 KB 设置重要度权重（默认相同）。某些场景下用户希望 KB A 的结果优先于 KB B，权重就有用。

折叠展示。多 KB 并联结果在前端按 KB 分组展示。每个 KB 一个折叠区，能看到这个 KB 命中了哪些 chunk、score 多少。用户能直观判断哪个 KB 提供了主要答案。

国产化支持下的多 KB 并联。混选国产 SQL 库（达梦、金仓）跟文档库时，方言适配在 structured adapter 内部，不影响并联。混选国产向量库（RT、Relyt）时，外部连接器 adapter 处理。

WPS AI 插件 chayuan-wps 同样支持多 KB 并联。在 WPS 文字里写报告时勾上几个相关 KB，引用气泡按 KB 分类展示，每个 KB 的来源能独立展开。

多 KB 并联是 chayuan-desktop 在多源知识管理上的核心能力。免费开源的AI软件 想做到 一个问句覆盖多个数据源，并联检索是必经之路。chayuan-desktop 的实现把延迟、上下文、错误隔离都处理到位。
