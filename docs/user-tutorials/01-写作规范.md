# 察元OS 用户教程写作规范（user-tutorials）

> 本规范是 `docs/user-tutorials/` 教程集的写作铁律。**写任何一篇教程前必读本规范 + `00-功能点清单.md`。**
> 核心要求（用户裁定）：**每一项都要写真实步骤，不许瞎编，全面解剖。**

## 一、事实纪律（防瞎编的硬规则）

1. **没查过代码的事实一个字不许写。** 按钮/菜单/字段/提示语的真实文案、UI 入口路径、行为顺序、端口号、文件路径，全部以 main 当前代码为准。禁止凭「常识」或模型先验补步骤。
2. **查证顺序（每类事实去哪查）**：

   | 要写的事实 | 权威来源 |
   |---|---|
   | 按钮/菜单/提示语文案 | `packages/i18n/src/dicts/`（按域：`pet.js`/`petchat.js`/`petgroup.js`/`modelsettings.js`/`models.js`/`wizard.js`/`settings.js`/`kb.js`/`sdapp.js`/`petstore.js` 等） |
   | 设置页分区与入口 | `dsh-plugin/src/desktop/app/SystemSettings.jsx`（SECTIONS）＋对应 `app/*.jsx` |
   | 灵宠/群聊流程 | `dsh-plugin/src/desktop/pet/`（PetLayer/AddPetModal、groupEngine、PetGroupApp） |
   | 端口号 | `packages/ports/src/index.js` + `docs/port-registry.md`（**禁手写端口字面量**） |
   | 模型注入五家写入面 | `docs/agent-model-inject-plan.md`（内部权威，改写前必读） |
   | 智能体名单/安装/能力 | `packages/agent-registry/src/index.js`（单一真源） |
   | KB 对外服务/健康检查 | `chatop-kb/src/service.js`、`chatop-kb/src/routes.js` |
   | 密码找回三条路 | `desktop/src/main/recovery-*.ts`、`dsh-plugin/src/desktop/components/RecoveryPanel.jsx`、`docs/password-recovery-plan.md` |
   | 既有教程素材 | `docs/help/**`（可复用，但口径以 main 代码复核为准） |
   | 坑与排障素材 | `docs/help/troubleshooting/`、`docs/chatop-test-report-*.md`、`docs/*-plan.md` |

3. **查不到就不写。** 某一步无法从代码确认时：省略该步并在交付说明里列出「未能核实项」，或标 `TODO(待真机确认)`。**宁缺勿编。**
4. **禁止猜测措辞**：正文不得出现「应该会」「大概」「可能是」描述操作结果；结果要么写实测/源码确认的行为，要么不写。
5. **每篇末尾必须有「事实来源」节**：列出本篇实际读过并引用的源码/文档路径（相对仓库根）。没有来源的篇不许交付。
6. **品牌与口径**：品牌拼写 chaOffice（禁 chatOffice）；应用名用产品内真名（宠物群聊、文生图、察元AI Office、跨终端互联等，以 i18n 文案为准）；版本基线 main。

## 二、文件与命名

- 文件名：`<清单编号>-<篇名>.md`，编号沿用 `00-功能点清单.md`（如 `M1-模型设置向导.md`、`K11-知识库引用链路健康检查.md`），chabot 侧按编号对账。
- frontmatter（固定六字段）：

```yaml
---
id: M1
title: 模型设置向导（首次配置四步走）
entry: 首次登录桌面自动弹出；重跑：设置→模型→设置向导
level: P0
tags: [模型, 向导, 首次配置]
status: draft        # draft → reviewed（用户审过后改）
---
```

## 三、正文固定结构（六节，顺序不许变）

```markdown
## 一句话说明
<这个功能是什么、干什么用的，一两句>

## 适用场景
<什么人、什么时候、遇到什么问题需要本教程；含 2-3 个典型提问（chabot 语料视角）>

## 前置条件
<版本/形态/依赖：如需先配好厂商密钥、需桌面形态、首次需下载约 2GB 权重等>

## 操作步骤
<编号步骤，全面解剖。每步 = 在哪（入口/界面位置）→ 做什么（真实按钮文案加引号）
→ 看到什么（界面反馈/下一屏）。涉及填写字段时逐字段说明含义与默认值；
涉及端口/路径时写真实值。步骤末尾必须有「验证」小节：做完后如何确认成功。>

### 验证
<可操作的确认动作，如：浏览器打开 http://127.0.0.1:52582/health 应返回……>

## 常见问题
<≥3 条，来自 docs 坑清单/排障文档/测试报告；一问一答，答给用户动作>

## 形态差异
<仅当桌面/web/docker/信创行为不同时保留本节，否则整节省略>
```

「事实来源」节放在六节之后（不属于正文结构，是合规记录）。

## 四、写完必做：三查自审

1. **文案查**：正文引用的每个按钮/提示语回 i18n dict 核对原文；
2. **端口/路径查**：所有端口对 `packages/ports`，所有配置文件路径对 agent-registry / agent-model-inject-plan；
3. **行为查**：步骤顺序与分支（成功/失败态）对源码流程走一遍，help 既有教程交叉对照，冲突以代码为准。

自审发现的问题当场修，修完在交付消息里报告：本篇来源清单、未核实项（如有）、与 help 的口径差异（如有）。

## 五、批次与并行

- 批次：P0（22 篇）→ P1（34 篇）→ P2（30 篇），见清单「教程批次计划」。
- 并行建议：**一个会话写 3-5 篇同域教程**（事实来源重叠、上下文省），不要一个会话写全量。
- 同域多篇的事实来源常相同（如同一个 dict 文件），同会话写可复用查证结果。

## 六、修改既有教程

产品改版后更新教程：改步骤 → 同步 `status: reviewed` 改回 `draft` → 更新 `updated` 日期 → 重跑三查。删除功能：整篇移除并在清单同步删行（清单与教程篇数对账）。
